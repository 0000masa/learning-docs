# Linuxのパッケージ管理とダウンロード — 道具ごとに「取得・展開・配置・記録」のどこを担当するかが違う

「dnfとaptは何が違うのか、なぜURLを指定しなくてもダウンロードできるのか、curl／wgetや`sudo install`は何をしているのか？」という疑問に答えるノート。結論を先に言うと：

- **パッケージを配る場所がリポジトリ（npmではレジストリ）、その中にある一覧がカタログ、自分のサーバーに何が入っているかの記録が台帳。** リポジトリは配布元ごとに立てるもので、世界中のリストはない。どの配布元を信用するかは、人間が`.repo`と公開鍵を足して決める（1章）。
- **ソフトウェアが使えるようになるまでには、①取得・②展開・③配置・④記録の4段階がある。** このノートの疑問のほとんどは「その道具がどの段階を担当しているか」の違いとして説明できる（2章）。
- **ダウンロードとインストールは別のもの。** ダウンロードは①取得だけで、`PATH`に含まれる場所に③配置して初めて使える状態になる（3章）。
- **dnfとaptの違いは、ディストリビューションの系統の違い。** Red Hat系（Amazon Linuxなど）は`.rpm`とdnf、Debian系（Ubuntuなど）は`.deb`とaptを使う（4章）。
- **rpm／dpkgは手元のパッケージを展開・配置・記録する低レベルの道具、dnf／aptはリポジトリから取得して依存関係を解決する高レベルの道具。** dnf／aptは②〜④をrpm／dpkgに任せる（5章）。
- **dnfやaptがURLなしで動くのは、OSを入れた時点で`/etc/yum.repos.d/`などの設定ファイルにリポジトリのURLが書いてあるから。** npmも同じで、レジストリのURLが前もって設定されている（6章）。
- **カタログは「ダウンロードできるもの」のリストで、package.jsonは「欲しいもの」のリスト。** aptは`apt update`のときだけカタログを更新し、dnfは期限が切れると自動で更新する。Amazon Linux 2023では、カタログがリリースのバージョンに固定される（7章）。
- **dnf／aptは実行したディレクトリに関係なくパッケージに書かれた場所に置くが、curl／wgetは今いるディレクトリに保存する。** 手作業で入れるものは、dnfとぶつからない`/usr/local/bin`に置く（8章）。
- **curlは「HTTPで話すための道具」、wgetは「ファイルを取ってくるための道具」。** リポジトリにない、リポジトリの版が古い、パッケージではない、のいずれかのときに使う（9章）。
- **`.tar.gz`や`.zip`で配布されているものは展開が必要。** dnfは`.rpm`の展開を中で行っているので意識しないだけ。展開は元のファイルを読んで新しいファイルを書き出すことで、元のファイルは変わらない（`gunzip`だけは元のファイルを消す）（10章）。
- **`sudo install`の`install`はcoreutilsのコマンドで、③配置（コピーと権限の設定）だけを行う。** `dnf install`／`apt install`／`npm install`は①〜④を全部行う（11章）。
- **Terraformは、wgetで取ってきて手作業で入れることも、リポジトリを足してdnfで入れることもできる。** 違いは、署名の検証、置き場所、台帳の記録、更新と削除のしかたに出る（12章）。

## 0. どこで出てきたか

EC2でPHPを更新したときに`dnf`を使ったことをきっかけに、次のような疑問が出た。

- dnfとapt、rpmとdpkgは何が違うのか
- dnfやaptは、なぜURLを指定しなくてもダウンロードできるのか。npmと同じようなものか
- curlやwgetでダウンロードするものがあるのはなぜか。curlとwgetは何が違うのか
- ダウンロードしたものはどこに置かれるのか。どのディレクトリでコマンドを実行しても同じか
- 「ダウンロード」と「インストール」は別の意味なのか
- `sudo install`の`install`と、`dnf install`／`apt install`／`npm install`の`install`は何が違うのか

コマンドの例は**Amazon Linux 2023（dnf）**で書く。Ubuntu（apt）の場合は、各節にある対応表を見ること。

全体を通して、次の2つを例として使う。

- **dnfで入れるPHP**：パッケージ管理に任せて入れるもの
- **Terraform**：wgetで取ってきて手作業で入れる方法と、リポジトリを追加してdnfで入れる方法の両方を比べる

## 1. 用語：パッケージ・カタログ・リポジトリ・レジストリ・台帳

このノートで何度も出てくる言葉を、先に整理しておく。

| 用語 | 意味 | たとえると | 例 |
| --- | --- | --- | --- |
| **パッケージ** | 1つのソフトウェアのファイル一式に、名前・バージョン・依存関係などの説明書きを付けて、**1つのファイル**にまとめたもの | 箱に入った商品 | `php8.2-cli-8.2.xx….rpm`、`express-4.x.x.tgz` |
| **カタログ** | リポジトリにあるパッケージの**説明書きだけを集めた一覧**。中身（実行ファイルなど）は入っていない。1つのファイルではなく、**複数のファイルの集まり** | 通販のカタログ | dnfの`repodata/`、aptの`Packages.gz`など |
| **リポジトリ** | パッケージとカタログを置いて配布している**場所**（サーバーの中のディレクトリ）。OSのパッケージ管理（dnf／apt）で使う呼び方 | 倉庫（商品とカタログが置いてある） | Amazon Linuxのリポジトリ、HashiCorpのリポジトリ |
| **レジストリ** | リポジトリと同じ役割のもの。npmやDockerで使う呼び方 | 同上 | `https://registry.npmjs.org/` |
| **台帳** | **自分のサーバーに**インストール済みのパッケージの記録。rpm／dpkgが管理する | 自宅の持ち物リスト | `/var/lib/rpm/`、`/var/lib/dpkg/` |

関係を図にすると次のようになる。

```
【配布元のサーバー】                                  【自分のサーバー】
リポジトリ（レジストリ）
├── カタログ（何があるかの一覧）  ──dnf/aptが取得──▶  カタログのコピー（/var/cache/dnf/）
└── パッケージ（.rpm がたくさん） ──必要な分だけ──▶  rpm/dpkg が展開・配置 ──▶ 台帳に記録（/var/lib/rpm/）
```

### カタログはリポジトリの中にある

カタログを取ってくる先も、パッケージを取ってくる先も、**同じリポジトリ**である。リポジトリの中身は、大きく「カタログ」と「パッケージ」の2つに分かれている。

```
dnf のリポジトリ（例）
https://…/リポジトリ/
├── repodata/                ← カタログ
│   ├── repomd.xml             （目次）
│   ├── primary.xml.gz         （パッケージの一覧・依存関係）
│   ├── filelists.xml.gz       （各パッケージのファイルの一覧）
│   └── updateinfo.xml.gz      （セキュリティ情報）
└── Packages/                ← パッケージ
    ├── php8.2-cli-….rpm
    └── nginx-….rpm
```

```
apt のリポジトリ（例）
http://archive.ubuntu.com/ubuntu/
├── dists/                   ← カタログ
│   └── noble/
│       ├── InRelease          （目次。署名付き）
│       └── main/binary-amd64/
│           └── Packages.gz    （パッケージの一覧・依存関係）
└── pool/                    ← パッケージ
    └── main/n/nginx/
        └── nginx_1.24….deb
```

カタログが複数のファイルに分かれているのは、用途ごとに必要な情報だけを取れるようにするためである。dnfはまず目次（`repomd.xml`）を取り、そこに書かれた場所から必要な一覧のファイルを取る。

### URLの組み立て方：カタログには相対パスしか書いていない

リポジトリの**URLが書いてあるのは`.repo`（設定ファイル）のほう**で、カタログではない。カタログに書いてあるのは、**リポジトリの中での相対的な場所**だけである。dnfは次の3段階でURLを組み立てている。

```
① .repo（自分のサーバーにある）
   baseurl=https://example.com/repo/          ← リポジトリの URL（ここだけが完全な URL）

② repodata/repomd.xml（目次。リポジトリにある）
   dnf は「baseurl + /repodata/repomd.xml」という決まった場所を見に行く
   中身： <location href="repodata/xxxx-primary.xml.gz"/>   ← 相対パス

③ repodata/xxxx-primary.xml.gz（カタログ本体。リポジトリにある）
   中身： <name>php8.2-cli</name> … <location href="Packages/php8.2-cli-8.2.xx….rpm"/>  ← 相対パス
```

dnfは、①の`baseurl`に、②③に書かれた相対パスをつなげて、実際のURLを作る。

```
https://example.com/repo/ + repodata/repomd.xml           → 目次のURL
https://example.com/repo/ + repodata/xxxx-primary.xml.gz  → カタログ本体のURL
https://example.com/repo/ + Packages/php8.2-cli-….rpm      → パッケージのURL
```

目次（`repomd.xml`）の場所は、どこにも書いていない。**「`baseurl`の下の`repodata/repomd.xml`に置く」という決まり**になっているので、dnfはそこを見に行く。だから`.repo`には、リポジトリの入口のURLを1つ書くだけで済む。

カタログを相対パスにしているのは、**ミラーのため**である。カタログに完全なURLを書いてしまうと、ミラー（同じ中身を複製したサーバー）ごとにカタログを書き換える必要がある。相対パスなら、同じカタログのファイルをそのままコピーするだけで、どのミラーでも使える。どのミラーから取るかによって変わるのは、①の入口のURLだけである。

aptも同じ形をしている。

| 段階 | dnf | apt |
| --- | --- | --- |
| リポジトリのURL（完全なURL） | `.repo`の`baseurl`／`mirrorlist` | `/etc/apt/sources.list.d/*`に書かれたURL |
| 目次 | `repodata/repomd.xml`（決まった場所） | `dists/noble/InRelease`（決まった場所） |
| 目次に書いてあるもの | カタログ本体のファイルの相対パス | `main/binary-amd64/Packages.gz`などの相対パス |
| カタログ本体に書いてあるもの | `location href="Packages/….rpm"` | `Filename: pool/main/n/nginx/nginx_….deb` |

| ファイル | 中身 | URLについて書いてあること |
| --- | --- | --- |
| `.repo`（aptでは`sources.list.d/*`） | どのリポジトリを使うか | リポジトリの**入口のURL** |
| カタログ | どのパッケージがあるか | リポジトリの中での**相対パス**だけ |

npmのレジストリには、このような「全部入りのカタログのファイル」はない。`npm install express`のたびに、レジストリに「expressの情報をください」と1件ずつ問い合わせる（`https://registry.npmjs.org/express`にアクセスすると、そのJSONが返ってくる）。7章で「npmはカタログを手元に持たない」と書いているのはこのためである。

### リポジトリの存在はどこで知るのか

dnfは、何も知らない状態から始めるわけではない。**OSをインストールした時点（EC2ならAMIから起動した時点）で、リポジトリの設定ファイルと公開鍵がすでにディスクに入っている**。

```
AMI（OSのイメージ）に最初から入っているもの
├── /etc/yum.repos.d/amazonlinux.repo               ← リポジトリのURL
└── /etc/pki/rpm-gpg/RPM-GPG-KEY-amazon-linux-2023  ← 署名を検証する公開鍵
```

この設定ファイル自体も、パッケージとしてインストールされたものである。

```bash
rpm -qf /etc/yum.repos.d/amazonlinux.repo
# → この .repo を置いたパッケージの名前が表示される
```

つまりリポジトリの場所は、**OSを作ったAmazonが、OSの中にあらかじめ書き込んで配っている**。dnfが最初から知っている必要があるのはこの設定ファイルだけで、あとはすべてそこからたどる。

HashiCorpのような**追加のリポジトリは、人間が配布元のドキュメントを読んで知り**、`.repo`を足す（12章B）。ここは自動ではない。

#### このサーバーのリポジトリのリスト＝`/etc/yum.repos.d/`

`/etc/yum.repos.d/`にある`.repo`ファイル全部が、**このサーバーが使うリポジトリのリスト**である。

```bash
dnf repolist --all
# repo id                        repo name                       status
# amazonlinux                    Amazon Linux 2023 repository    enabled
# amazonlinux-debuginfo          ... debuginfo                   disabled
# amazonlinux-source             ... source                      disabled
# kernel-livepatch               ... Kernel Livepatch            enabled
```

`--all`を付けると、`enabled=0`（使わない）になっているリポジトリも表示される。Amazon Linux 2023には、デバッグ用やソースコード用のリポジトリが、**書いてはあるけれど無効**の状態で入っている。こうしたリポジトリは、`.repo`を足さなくても有効にするだけで使える。

```bash
sudo dnf config-manager --set-enabled amazonlinux-source
```

つまり、ディスクにあるリストには「使っているリポジトリ」と「存在は知っているが使っていないリポジトリ」の両方が入っている。

#### 世界中のリポジトリのリストはない

「このサーバーのリスト」はあるが、「世界中のリポジトリのリスト」のようなファイルはない。**リポジトリは誰でも勝手に作れる**からである。

リポジトリの正体は、カタログ（`repodata/`）とパッケージ（`Packages/`）を置いたディレクトリをHTTPで公開したものにすぎない。どこかに登録する必要はなく、HashiCorpもDockerも、自分のサーバーに置いて公開しているだけである。

| | npm | dnf／apt |
| --- | --- | --- |
| 配布の場所 | 世界で1つの大きなレジストリに、みんなが**登録する** | 配布元ごとに**自分でリポジトリを立てる** |
| 「全部のリスト」 | レジストリそのものが全部のリスト（`npm search`で探せる） | ない |
| 新しい配布元のものを使うとき：何を使いたいかの指定 | 必要（`npm install パッケージ名`。package.jsonに追加される） | 必要（`dnf install パッケージ名`。ファイルには残らない） |
| 新しい配布元のものを使うとき：どこから取るかの設定 | **不要**（どの配布元のものも同じレジストリにある） | **必要**（その配布元のリポジトリを`.repo`で足し、公開鍵も入れる） |

どちらも「何を使いたいか」は指定する必要がある。大きな違いは、dnf／aptでは**どこから取るか（配布元のリポジトリ）と、それを信用するか（公開鍵）**の設定も、自分で足す必要があることである。npmでは、配布元が誰であっても同じレジストリに登録されているので、この設定はいらない。

人間向けに探せるWebサイトならある（UbuntuのPPAを一覧できるLaunchpad、FedoraのCOPRなど）。ただし、どれもdnfやaptが自動で参照するファイルではない。

#### 自動にしないのはわざと

リポジトリを足すときは、**その配布元の公開鍵も一緒に入れる**。これは「この配布元が署名したものなら、サーバーに入れてよい」と信用することを意味する。パッケージのインストールは、中に入っているスクリプトも含めてroot権限で動くので、配布元を信用するのはサーバーの全権限を預けるのと同じである。

もし「世界中のリポジトリのリスト」があって、dnfが自動でそこから探しに行くとしたら、**誰が作ったかわからないリポジトリのパッケージが、root権限で入ってしまう**おそれがある。そのため、どの配布元を信用するかは人間が決めて、`.repo`と公開鍵を手で足す作りになっている。

「ここは自動ではない」というのは、手間がかかるという話ではなく、**信用するかどうかを人間が判断する場所**だという意味である。

### 新しいパッケージが出たことはどこで知るのか

**誰からも通知は来ない**。次のような仕組みになっている。

1. 配布元は、新しいパッケージをリポジトリの`Packages/`に置き、**同じURLにあるカタログのファイルを新しい内容で置き換える**
2. dnfは、ときどき（期限が切れたら）**同じURLのカタログを取り直す**
3. 取り直したカタログに新しいものが載っていれば、「新しく出た」とわかる

Webページを再読み込みすると、同じURLでも中身が更新されているのと同じである。こちらから取りに行く方式（プル型）で、向こうから知らせてくる方式（プッシュ型）ではない。

毎回カタログを全部取り直すのは無駄なので、dnfは小さな**目次（`repomd.xml`）だけを先に取る**。目次には各カタログのファイルのチェックサム（中身から計算した値）が書いてあり、手元のものと比べて、変わっていたときだけ本体を取り直す。

たどる順番をまとめると次のようになる。

```
① AMI に入っている .repo を読む            … 最初から知っている必要があるのはこれだけ
     ↓ URL がわかる
② （mirrorlist なら）ミラーの一覧を取る     … どのサーバーから取るかを決める
     ↓
③ repodata/repomd.xml（目次）を取る         … カタログのどのファイルが、どこにあるか
     ↓ 手元のものと変わっていれば
④ primary.xml.gz など（カタログ本体）を取る … どのパッケージが、どこにあるか
     ↓
⑤ Packages/….rpm（パッケージ）を取る
```

通販でたとえると、「店の住所は入会したとき（OSをインストールしたとき）にもらった会員証に書いてある。店は同じ場所でカタログを最新版に差し替えている。こちらはときどき店に行って最新版をもらう」という関係である。

### `.repo`を足す必要があるのはどんなときか

`.repo`を足す必要があるかどうかは、「新しいバージョンか、新しい種類か」では決まらない。**そのパッケージがどのリポジトリで配られているか**で決まる。

| 出てきたもの | 例 | どう見えるようになるか |
| --- | --- | --- |
| 同じリポジトリの、既存のパッケージの新しいバージョン | `php8.2-cli`の8.2.xx → 8.2.yy | カタログを取り直すだけ |
| 同じリポジトリの、**新しい種類のパッケージ** | Amazon Linuxのリポジトリに`php8.4`が追加された | **カタログを取り直すだけ**（カタログに新しい行が増える） |
| **別のリポジトリ**にあるパッケージ | HashiCorpが配っている`terraform` | `.repo`を足す必要がある |

カタログは「そのリポジトリにあるもの全部」の一覧なので、配布元が同じリポジトリに新しい種類のパッケージを置けば、カタログにもその行が増える。`.repo`を足すのは、**今まで見ていなかった店（配布元）の商品が欲しいとき**である。

ただし、Amazon Linux 2023ではカタログがリリースのバージョンで固定されているので（7章）、同じURLを取り直しても**そのリリースの範囲の更新**しか見えない。新しいリリースで追加されたパッケージは、`--releasever`で新しいリリースに移るまで見えない。新しいリリースが出たかどうかは、`dnf check-release-update`で確かめる。

`.repo`を足すのに、専用のコマンドが必要なわけではない。`dnf config-manager --add-repo URL`は「`.repo`ファイルをダウンロードして`/etc/yum.repos.d/`に置く」だけで、手でファイルを作っても同じである。リポジトリの設定ファイルを中身にしたパッケージを`dnf install`して足す方式（Fedora系のEPELの`epel-release`など）もある。

### リポジトリとレジストリの違い

役割は同じで、**「パッケージを置いて配布している場所」**である。違いは主に、どの世界で使われる呼び方かである。

| | リポジトリ | レジストリ |
| --- | --- | --- |
| 使われる世界 | OSのパッケージ管理（dnf、apt） | 言語やコンテナのパッケージ管理（npm、Docker Hub、Amazon ECRなど） |
| 中身の取り方 | カタログのファイルをまとめて取ってきて、手元で探す | パッケージの名前を指定して、1件ずつ問い合わせる |
| 数 | 配布元ごとに別々のリポジトリがあり、複数を同時に使うのが普通 | 1つの大きなレジストリに、世界中の人がパッケージを**登録（register）**するのが普通 |

「レジストリ（registry）」はもともと「登録簿」という意味である。npmでは誰でも自分のパッケージを名前を付けて登録できるので、「名前を登録して管理している場所」という面が強く、この呼び方になっている。ただ、実際の作業では**同じものと考えて問題ない**。

## 2. 全体像：ソフトウェアが使えるようになるまでの4段階

ソフトウェアがサーバーで使えるようになるまでには、次の4つの段階がある。

| 段階 | やること | 例 |
| --- | --- | --- |
| ①取得 | ネットワークの向こうからファイルを手元のディスクに持ってくる | `terraform_1.14.3_linux_amd64.zip`を`/tmp`に保存する |
| ②展開 | まとめられた・圧縮されたファイルを元の形に戻す | zipを解凍して`terraform`という実行ファイルを取り出す |
| ③配置 | 決まった場所に、決まった権限で置く | `/usr/local/bin/terraform`に、実行できる権限で置く |
| ④記録 | 「何を、どのバージョンで、どこに置いたか」を台帳に残す | rpmの台帳に「php8.2-cliの8.2.xxが入っていて、`/usr/bin/php`はこのパッケージのもの」と書く |

このノートで出てくる道具が、それぞれどの段階を担当しているかをまとめると次のようになる。

| 道具 | ①取得 | ②展開 | ③配置 | ④記録 |
| --- | --- | --- | --- | --- |
| curl／wget | ✅ | ― | ― | ― |
| tar／unzip | ― | ✅ | ― | ― |
| `install`コマンド | ― | ― | ✅（コピーと権限の設定だけ） | ― |
| rpm／dpkg | ― | ✅ | ✅ | ✅ |
| dnf／apt | ✅（リポジトリから） | rpm／dpkgに任せる | rpm／dpkgに任せる | rpm／dpkgに任せる |
| npm | ✅ | ✅ | ✅（`node_modules`に置く） | ✅（`package-lock.json`に書く） |

このノートの疑問のほとんどは、**「その道具がどの段階を担当しているか」**の違いとして説明できる。

- curlやwgetは①しかしない。だから、置き場所も記録も自分で面倒を見る必要がある
- `install`コマンドは③しかしない。だから、何もダウンロードしない
- dnfやaptは①〜④を全部やってくれる（②〜④は中でrpm／dpkgを呼んで行う）

## 3. 「ダウンロード」と「インストール」は別のもの

2章の4段階で言うと、次のように分かれる。

- **ダウンロード**：①取得のこと。ファイルを手元のディスクに持ってくるだけ
- **インストール**：③配置（と④記録）のこと。ソフトウェアを**使える状態にする**こと

ダウンロードしただけでは、まだ使えない。たとえば`/tmp`にTerraformのzipをダウンロードしても、そのままでは`terraform`コマンドは動かない。

```bash
cd /tmp
wget https://releases.hashicorp.com/terraform/1.14.3/terraform_1.14.3_linux_amd64.zip
terraform version
# bash: terraform: command not found   ← ダウンロードしただけでは使えない
```

展開して実行ファイルを取り出しても、`/tmp`にある限りは`./terraform`のように**場所を指定しないと**動かない。シェルはコマンド名を、環境変数`PATH`に並んでいるディレクトリ（`/usr/local/bin`、`/usr/bin`など）の中からしか探さないからである。

```bash
echo $PATH
# /usr/local/bin:/usr/bin:/usr/local/sbin:/usr/sbin
```

`PATH`に含まれる場所に置いて、初めて`terraform`とだけ打てば動く状態、つまり「インストールされた」状態になる。

`dnf install`や`npm install`は、ダウンロードとインストールを1つのコマンドでまとめて行うので、2つの区別が見えにくくなっている。

## 4. なぜディストリビューションによって道具が違うのか

Linuxのディストリビューション（Linuxカーネルに、コマンドやライブラリを組み合わせて配布しているもの）は、大きく2つの系統に分かれる。系統ごとに**パッケージファイルの形式が違う**ので、使う道具も違う。

| 系統 | 主なディストリビューション | パッケージの形式 | 低レベルの道具 | 高レベルの道具 |
| --- | --- | --- | --- | --- |
| Red Hat系 | RHEL、Fedora、AlmaLinux、Rocky Linux、**Amazon Linux** | `.rpm` | `rpm` | `dnf`（以前は`yum`。Amazon Linux 2は`yum`） |
| Debian系 | Debian、**Ubuntu** | `.deb` | `dpkg` | `apt`（`apt-get`） |

**パッケージ**とは、ソフトウェアのファイル一式に、「何というソフトウェアの、どのバージョンか」「何に依存しているか」「どこに何を置くか」といった情報を付けて、1つのファイルにまとめたものである。`.rpm`と`.deb`はこのまとめ方の形式が違うので、互いに読めない。Ubuntuで`.rpm`は（そのままでは）使えず、Amazon Linuxで`.deb`は使えない。

この2つ以外にも、Alpine Linux（Dockerのイメージでよく使う）の`apk`、Arch Linuxの`pacman`などがあるが、考え方は同じである。

## 5. rpm／dpkgとdnf／aptの違い

どちらもパッケージを扱う道具だが、担当する段階が違う。

| | 低レベル（rpm／dpkg） | 高レベル（dnf／apt） |
| --- | --- | --- |
| 担当する段階 | ②展開、③配置、④記録 | ①取得（＋依存関係の解決）。②〜④はrpm／dpkgに任せる |
| 扱うもの | **手元にある**パッケージファイル | **リポジトリにある**パッケージ |
| 依存関係 | 調べるだけ。足りなければエラーで止まる | 足りないものを探して、一緒に入れる |

低レベルの道具だけでインストールすると、依存関係で困る。

```bash
# 手元にある .rpm を rpm で直接入れる
sudo rpm -i php8.2-cli-8.2.xx.rpm
# error: Failed dependencies:
#     php8.2-common = 8.2.xx is needed by php8.2-cli-8.2.xx
#     ...               ← 足りないものを自分で探してこいと言われる
```

dnfは、足りないものをリポジトリから探してきて、まとめてrpmに渡す。手元の`.rpm`ファイルを入れるときも、dnfに渡せば依存関係を解決してくれる。

```bash
sudo dnf install ./php8.2-cli-8.2.xx.rpm   # 足りない php8.2-common などはリポジトリから取ってくる
```

普段の作業では高レベルの道具（dnf／apt）を使う。低レベルの道具（rpm／dpkg）は、主に**④記録（台帳）を調べる**ときに使う。

```bash
# このファイルはどのパッケージのものか
rpm -qf /usr/bin/php
# php8.2-cli-8.2.xx-1.amzn2023.0.1.x86_64

# インストール済みのパッケージの一覧
rpm -qa 'php*'

# このパッケージはどこに何を置いたか
rpm -ql php8.2-cli
```

| やりたいこと | Amazon Linux 2023 | Ubuntu |
| --- | --- | --- |
| このファイルはどのパッケージのものか | `rpm -qf /usr/bin/php` | `dpkg -S /usr/bin/php` |
| インストール済みの一覧 | `rpm -qa` | `dpkg -l` |
| パッケージが置いたファイルの一覧 | `rpm -ql パッケージ名` | `dpkg -L パッケージ名` |
| 台帳の場所 | `/var/lib/rpm/` | `/var/lib/dpkg/` |

### オプションの意味

オプションは、長い名前（`--query`など）の頭文字を取った短い形である。長い名前で書いても同じように動く。

**rpm**

rpmは、最初のオプションで「何をするか」（モード）を決め、2つ目以降で「何を対象にするか」「何を表示するか」を決める。`-qf`は`-q`と`-f`の2つをまとめて書いたもので、`rpm -q -f`と同じである。

| オプション | 長い名前 | 意味 |
| --- | --- | --- |
| `-q` | `--query` | 台帳を**問い合わせる**モード。何も変更せず、調べるだけ |
| `-f` | `--file` | `-q`と組み合わせて使う。対象を**ファイル**で指定し、そのファイルを持っているパッケージを調べる |
| `-a` | `--all` | `-q`と組み合わせて使う。インストール済みの**すべて**のパッケージを対象にする。`rpm -qa 'php*'`のようにパターンで絞り込める |
| `-l` | `--list` | `-q`と組み合わせて使う。パッケージが置いたファイルを**一覧表示**する |
| `-i` | `--install` | パッケージファイルを**インストール**するモード（5章の`rpm -i`）。依存関係は解決しない |

`-i`は`-q`と組み合わせると`--info`（パッケージの詳しい情報を表示する）という別の意味になる。たとえば`rpm -qi php8.2-cli`である。rpmの短いオプションは、モードによって意味が変わることがある。

**dpkg**

dpkgは、1つのオプションで「何をするか」が決まる。rpmと違い、大文字と小文字で別のオプションになる。

| オプション | 長い名前 | 意味 |
| --- | --- | --- |
| `-S` | `--search` | ファイルのパスで台帳を**検索**し、そのファイルを持っているパッケージを表示する |
| `-l` | `--list` | インストール済みのパッケージを**一覧表示**する。`dpkg -l 'php*'`のようにパターンで絞り込める |
| `-L` | `--listfiles` | パッケージが置いた**ファイルを一覧表示**する |

`-l`（小文字）は「パッケージの一覧」、`-L`（大文字）は「ファイルの一覧」である。rpmでは`-qa`と`-ql`に当たる。

## 6. dnfやaptは、なぜURLを指定しなくてもダウンロードできるのか

### `dnf install php`で起きていること

`dnf install php`を実行すると、中では次のことが順番に起きている。

```
dnf install php
 ① /etc/yum.repos.d/*.repo を読む          … 「どのサーバーから取るか」がここに書いてある（URLはここにある）
 ② リポジトリのカタログを取得               … どのパッケージの、どのバージョンがあるか、何に依存しているか
 ③ 依存関係を解決                           … php には php-common などが必要、と計算する
 ④ .rpm ファイルをダウンロード               … ②のカタログに書いてあるパスから取る
 ⑤ GPG署名を検証                            … 配布元が作った正しいファイルで、改ざんされていないかを確認する
 ⑥ rpm に渡して展開・配置・記録
```

URLを指定しなくてよいのは、**①の設定ファイルに前もって書いてあるから**である。「URLがいらない」のではなく、「OSを入れた時点でURLが書いてある」ということである。

### ①リポジトリの設定ファイル

どのリポジトリ（[1章](#1-用語パッケージカタログリポジトリレジストリ台帳)）を使うかは、設定ファイルに書いてある。

```bash
ls /etc/yum.repos.d/
# amazonlinux.repo  kernel-livepatch.repo
```

```ini
# /etc/yum.repos.d/amazonlinux.repo（抜粋・簡略化）
[amazonlinux]
name=Amazon Linux 2023 repository
mirrorlist=https://al2023-repos-$awsregion-....amazonaws.com/core/mirrors/$releasever/$basearch/mirror.list
enabled=1
gpgcheck=1
gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-amazon-linux-2023
```

| 項目 | 意味 |
| --- | --- |
| `[amazonlinux]` | このリポジトリの名前 |
| `mirrorlist`／`baseurl` | どこから取るか（URL） |
| `enabled=1` | このリポジトリを使う |
| `gpgcheck=1` | ダウンロードしたパッケージの署名を検証する |
| `gpgkey` | 検証に使う公開鍵の場所 |

`$releasever`（リリースのバージョン）や`$basearch`（CPUの種類。`x86_64`など）は、dnfが実行するときに実際の値に置き換える。`$releasever`は、7章で説明する「Amazon Linux 2023のカタログの固定」に関係する。

Ubuntuの場合は、`/etc/apt/sources.list.d/`の中に同じ役割のファイルがある。

### リポジトリは1つではない

リポジトリは、dnfやaptが持っているものではない。**パッケージを配っている側（Amazon、Ubuntu、HashiCorpなど）が持っている場所**である。dnfやaptは、設定ファイルに書かれた**複数のリポジトリを見に行く道具**である。

```
dnf ──┬─▶ amazonlinux（Amazonが配布：PHP、nginxなどOSの基本）
      ├─▶ kernel-livepatch（Amazonが配布：カーネルの修正）
      └─▶ hashicorp（HashiCorpが配布：Terraformなど）← 12章Bで追加するもの
```

`/etc/yum.repos.d/`に`.repo`ファイルが複数並んでいるのはこのためである。1つの`.repo`ファイルの中に、複数のリポジトリが書かれていることもある。

| 道具 | 最初から設定されているリポジトリ | 追加される例 | 一覧を見るコマンド |
| --- | --- | --- | --- |
| dnf（Amazon Linux 2023） | `amazonlinux`、`kernel-livepatch`など | HashiCorp、Docker | `dnf repolist` |
| apt（Ubuntu） | `noble`（main／universeなど）、`noble-updates`、`noble-security`など、**最初から複数** | ondrej/php（PPA）、HashiCorp | `apt-cache policy`（引数なし） |
| npm | `https://registry.npmjs.org/`の1つ | 名前の範囲（スコープ）ごとに別のレジストリ | `npm config list` |

```bash
dnf repolist
# repo id              repo name
# amazonlinux          Amazon Linux 2023 repository
# kernel-livepatch     Amazon Linux 2023 Kernel Livepatch repository
```

Ubuntuでは、セキュリティ修正だけを配るリポジトリ（`-security`）が、通常のものと分かれている。1つのOSの公式リポジトリでも、役割ごとに分けて複数持つのが普通である。

npmはふだん1つのレジストリだけを使うが、`.npmrc`に`@mycompany:registry=https://npm.mycompany.example/`のように書くと、「`@mycompany/`で始まるパッケージだけは社内のレジストリから取る」という使い分けができる。

### 1つのリポジトリにもURLが複数ある（ミラー）

上の設定ファイルの例で`baseurl`ではなく`mirrorlist`と書いてあったのは、1つのリポジトリにもURLが複数あるからである。

- **ミラー**：同じ中身を複製して置いているサーバー。世界中や各リージョンに置いて、近くて速いところから取れるようにする
- `mirrorlist`には、「ミラーのURLの一覧が書かれたファイル」の場所が書いてある。dnfはその中から使えるものを選ぶ

つまり、「リポジトリが複数ある」うえに、「1つのリポジトリにもミラーのURLが複数ある」という二重の構造になっている。

### 同じパッケージが複数のリポジトリにあるとき

複数のリポジトリを使うと、同じ名前のパッケージが複数のリポジトリにあることがある。たとえば、Ubuntuの標準リポジトリにもondrejのPPAにも`php8.2-fpm`がある、という場合である。

- **dnf**：基本は**一番新しいバージョン**を選ぶ。`.repo`に`priority=`を書くと、リポジトリの優先度を変えられる
- **apt**：リポジトリごとの優先度（pin priority）とバージョンの新しさで決める。`apt-cache policy php8.2-fpm`を実行すると、候補になるリポジトリと、選ばれるバージョンが表示される

```bash
# インストール済みのものを、どのリポジトリから入れたか（右端の @ の後ろ）
dnf list installed 'php*'
# php8.2-cli.x86_64    8.2.xx-1.amzn2023.0.1    @amazonlinux
```

「どこから入れたか」を確かめるコマンドが必要になるのは、このようにリポジトリが複数あるからである。

### ⑤GPG署名の検証

curlでファイルを取ってきても、それが**本当に配布元が作ったものか**はわからない。途中で書き換えられていても気付けない。dnfやaptは、これを署名で確認している。

- 配布元は、パッケージに**秘密鍵**で署名する。秘密鍵は配布元だけが持っている
- dnfは、手元にある配布元の**公開鍵**（設定ファイルの`gpgkey`）で署名を検証する
- 検証が通れば、「このファイルは正しい秘密鍵で署名されたもの」、つまり**配布元が作ったもので、途中で書き換えられていない**と言える

公開鍵は検証にしか使えず、公開鍵から署名を作ることはできない。そのため、公開鍵が誰に知られても問題はない。

### npmと同じようなものか

同じである。npmにも最初からリポジトリ（npmでは**レジストリ**と呼ぶ）が設定されている。

```bash
npm config get registry
# https://registry.npmjs.org/
```

`npm install express`がURLなしで動くのも、このレジストリのURLが前もって設定されているからである。設定は`.npmrc`で変えられる（社内用のレジストリを使うときなど）。①〜④の流れはdnfと同じ形をしている。

### リポジトリにないものは入れられない

dnfが入れられるのは、**①に書かれたリポジトリにあるものだけ**である。たとえばTerraformは、Amazon Linux 2023の標準のリポジトリにはない。

```bash
sudo dnf install terraform
# Error: Unable to find a match: terraform
```

この場合の選択肢は2つである。

1. **リポジトリを追加する**：配布元（HashiCorp）が用意しているリポジトリの設定ファイルを、①の`/etc/yum.repos.d/`に1つ増やす。そうすればdnfで入れられるようになる
2. **curlやwgetで取ってくる**：リポジトリを使わず、配布元のサイトからファイルを直接ダウンロードして、②〜③を自分で行う

両方のやり方は[12章](#12-通し例terraformを2通りで入れる)で比べる。

## 7. カタログ：「ダウンロードできるもの」のリスト

このノートでは、リポジトリが持っている「どのパッケージの、どのバージョンがあるか」の一覧を**カタログ**と呼ぶ。正式には、dnfでは**メタデータ**、aptでは**パッケージリスト**と呼ばれる。

### パッケージとカタログの違い

パッケージは「箱に入った商品」、カタログは「商品の一覧表」である。

パッケージは、実体としては**1つのファイル**（`.rpm`や`.deb`）で、中に「実際に置かれるファイル」と「そのパッケージ自身の説明書き」が入っている。

```
php8.2-cli-8.2.xx-1.amzn2023.x86_64.rpm   ← これ1つが「パッケージ」
├── 中身（実際に置かれるファイル）
│   ├── /usr/bin/php
│   └── /usr/share/man/man1/php.1.gz ...
└── 説明書き（パッケージ自身の情報）
    ├── 名前：php8.2-cli
    ├── バージョン：8.2.xx
    ├── 依存しているもの：php8.2-common など
    ├── 置くファイルの一覧
    └── 署名（配布元の秘密鍵で付けたもの）
```

カタログには中身（`/usr/bin/php`の実体）は入っていない。**各パッケージの説明書きだけを、リポジトリ全体から集めて並べたもの**である。

```
カタログ（リポジトリのメタデータ）
├── php8.2-cli    8.2.xx  依存：php8.2-common …  場所：Packages/php8.2-cli-8.2.xx….rpm
├── php8.2-fpm    8.2.xx  依存：php8.2-common …  場所：Packages/php8.2-fpm-8.2.xx….rpm
├── nginx         1.24.x  依存：…                 場所：Packages/nginx-1.24.x….rpm
└── …（数千件）
```

dnfはまずカタログを見て「何があって、何に依存していて、どこに置いてあるか」を調べ（6章の②③）、それから必要なパッケージのファイルだけをダウンロードする（6章の④）。

| | パッケージ | カタログ |
| --- | --- | --- |
| たとえると | 箱に入った商品 | 通販のカタログ（商品一覧） |
| 実体 | `.rpm`ファイル1つ（リポジトリの`Packages/`にあり、ダウンロードすると中身はそのままで`/var/cache/dnf/`の下にコピーされる。インストール後は通常消える。10章） | リポジトリにある一覧のファイル群（手元のコピーは`/var/cache/dnf/`） |
| 中身 | ソフトウェアのファイル＋そのパッケージの説明書き | 多数のパッケージの説明書きだけ |
| 何件分か | 1つのソフトウェア | リポジトリにあるもの全部 |
| ダウンロードされるとき | インストールするときに、必要なものだけ | カタログを更新するとき（`apt update`、dnfの自動更新） |

npmでも同じである。`express`というパッケージの実体は`express-4.x.x.tgz`というファイルで、中にJavaScriptのファイルと`express`自身のpackage.jsonが入っている。レジストリは、そうしたパッケージの情報をまとめた一覧を持っている。

「メタデータ」という言葉はどちらにも出てくるので、混乱しやすい言葉である。

- **パッケージ自身のメタデータ**：箱の中の説明書き（1件分）
- **リポジトリのメタデータ（＝カタログ）**：その説明書きをリポジトリ全体から集めた一覧

コマンドによって、どれを見ているかが違う。

```bash
dnf info php8.2-cli                # カタログを見る（リポジトリにあるもの。入れる前でも調べられる）
rpm -qi php8.2-cli                 # 台帳を見る（インストール済みのもの）
rpm -qip php8.2-cli-8.2.xx.rpm     # 手元にある .rpm ファイルそのものの説明書きを見る（-p = --package）
```

### package.jsonはカタログではない

npmにもdnfにも、リストは2種類ある。

| | 「**ダウンロードできるもの**」のリスト（カタログ） | 「**自分が欲しいもの**」のリスト |
| --- | --- | --- |
| npm | レジストリが持っている全パッケージの情報 | **package.json** |
| dnf | リポジトリのメタデータ | **ない** |
| apt | リポジトリのパッケージリスト | **ない** |

package.jsonは「このプロジェクトにはexpressの4系が必要」という**欲しいもののリスト**で、カタログではない。

dnfやaptには、package.jsonに当たるファイルはない。サーバー全体で1つの状態を持っていて、「今何が入っているか」はrpm／dpkgの台帳（④記録）が覚えているだけである。「このサーバーにはこれを入れる」という欲しいもののリストを残したいときは、手順書やシェルスクリプト、Dockerfile、Ansibleなどに自分で書く。

### カタログはどこにあって、いつ更新されるか

dnfとaptは、カタログの**コピーを手元に保存**している。npmは手元に保存しない。この違いのために、aptには「カタログを更新するコマンド」が必要になる。

| | カタログの置き場所 | 更新のしかた |
| --- | --- | --- |
| npm | 手元に持たない。`npm install`のたびに**レジストリに直接聞きに行く** | 更新する必要がない |
| apt | `/var/lib/apt/lists/` | **`apt update`を実行したときだけ**更新される |
| dnf | `/var/cache/dnf/` | **期限（`metadata_expire`）が切れていれば、`dnf install`などのときに自動で更新される**。手動で更新するなら`dnf makecache` |

#### 手元のどこに、どういう形で保存されるか

カタログは複数のファイルの集まりなので（1章）、取ってきた後も**別々のファイルのまま**保存される。並べ方はdnfとaptで違う。また、どちらも**取ってきたカタログを、速く探せる形に変換したファイル**を別に作っている。

**dnf（Amazon Linux 2023）：リポジトリごとにディレクトリを分ける**

```
/var/cache/dnf/
├── amazonlinux-xxxxxxxx/          ← リポジトリ「amazonlinux」の分
│   ├── repodata/                  ← 取ってきたカタログを、ほぼそのままの形で保存
│   │   ├── repomd.xml
│   │   ├── xxxx-primary.xml.gz
│   │   ├── xxxx-filelists.xml.gz
│   │   └── xxxx-updateinfo.xml.gz
│   └── packages/                  ← ダウンロードした .rpm（インストール後は基本的に消される）
├── amazonlinux.solv               ← カタログを、速く探せる形に変換したもの
├── amazonlinux-filenames.solvx
├── kernel-livepatch-xxxxxxxx/     ← 別のリポジトリは別のディレクトリ
└── kernel-livepatch.solv
```

- リポジトリの名前（`.repo`の`[amazonlinux]`）ごとにディレクトリが分かれ、その中の`repodata/`に、リポジトリにあったカタログのファイルがそのまま並ぶ。リポジトリ側の構成（1章の図）とほぼ同じ形
- `.solv`は、XMLのカタログを依存関係の計算用の形式に変換したもの。`dnf install`のたびにXMLを読み直すと遅いので、変換したものを使う

**apt（Ubuntu）：1つのディレクトリに、URLを元にした名前で並べる**

```
/var/lib/apt/lists/
├── archive.ubuntu.com_ubuntu_dists_noble_InRelease
├── archive.ubuntu.com_ubuntu_dists_noble_main_binary-amd64_Packages
├── archive.ubuntu.com_ubuntu_dists_noble-updates_InRelease
├── security.ubuntu.com_ubuntu_dists_noble-security_main_binary-amd64_Packages
├── ppa.launchpadcontent.net_ondrej_php_ubuntu_dists_noble_InRelease
└── …
/var/cache/apt/
├── pkgcache.bin                   ← カタログを、速く探せる形に変換したもの
└── archives/                      ← ダウンロードした .deb（apt clean で消える）
```

- リポジトリごとにディレクトリを分けず、**リポジトリ上のURLの`/`を`_`に置き換えたもの**をファイル名にして、全リポジトリ分を1つのディレクトリに並べる。ファイル名を見れば、どのリポジトリのどのカタログかがわかる
- `pkgcache.bin`が、dnfの`.solv`と同じ役割（変換して速く探せるようにしたもの）

| | dnf | apt |
| --- | --- | --- |
| 取ってきたカタログ | `/var/cache/dnf/<リポジトリ名>-<ハッシュ>/repodata/` | `/var/lib/apt/lists/`（URLを元にしたファイル名） |
| 分け方 | リポジトリごとにディレクトリ | 1つのディレクトリにまとめて、ファイル名で区別 |
| 速く探すための変換版 | `/var/cache/dnf/*.solv` | `/var/cache/apt/pkgcache.bin` |
| ダウンロードしたパッケージ | `/var/cache/dnf/…/packages/`（インストール後は基本的に消える） | `/var/cache/apt/archives/`（`apt clean`まで残る） |
| 全部消して取り直す | `sudo dnf clean all` → `sudo dnf makecache` | `sudo rm -rf /var/lib/apt/lists/*` → `sudo apt update` |

カタログもパッケージも、手元にあるのは**キャッシュ（取り直せるコピー）**である。消しても、次に取り直せば元に戻る。一方、**消してはいけないのは台帳（`/var/lib/rpm/`、`/var/lib/dpkg/`）**である。台帳は「このサーバーに何が入っているか」の唯一の記録で、リポジトリには同じものがない。

ディレクトリ名のハッシュの部分や細かいファイル名は、環境によって違う。EC2で`ls /var/cache/dnf/`を実行すると、自分の環境の実物を確認できる。

dnfやaptのインストールは、**手元のカタログにもとづいて**行われる。カタログに載っていないものは入れられず、カタログが古ければ古いバージョンが入る。

aptではこれが特に問題になる。`apt update`をしばらくしていないと、カタログに書かれているバージョンがリポジトリからすでに消えていて、ダウンロードが404エラーで失敗することがある。そのため、aptでは次のようにセットで書くのが定番である。

```bash
sudo apt update && sudo apt install php8.2-fpm
```

| やりたいこと | Amazon Linux 2023 | Ubuntu |
| --- | --- | --- |
| カタログを更新する | 自動（手動なら`dnf makecache`） | `apt update` |
| 新しいバージョンがあるか見る | `dnf check-update` | `apt list --upgradable` |
| インストールする | `dnf install php8.2` | `apt install php8.2` |
| 入っているものを全部新しくする | `dnf upgrade` | `apt upgrade` |
| 削除する | `dnf remove php8.2` | `apt remove php8.2` |
| リポジトリの設定ファイル | `/etc/yum.repos.d/*.repo` | `/etc/apt/sources.list.d/*` |

`apt update`と`apt upgrade`は名前が似ているが、まったく別のものである。`update`は**カタログを新しくする**だけで、ソフトウェアは1つも新しくならない。`upgrade`が**インストール済みのソフトウェアを新しくする**コマンドである。

### Amazon Linux 2023ではカタログが固定されている

Amazon Linux 2023では、カタログが**インスタンスを起動したときのリリースのバージョンに固定**されている。AWSはこれを「決定的なアップグレード（deterministic upgrades）」と呼んでいる。

6章の設定ファイルにあった`$releasever`が、その仕組みである。

```bash
# 今のサーバーが見ているリリースのバージョン
cat /etc/dnf/vars/releasever
# 2023.6.20241010
```

リポジトリのURLにこのバージョンが入るので、dnfは**このリリースのカタログしか見ない**。そのため、次のようなことが起きる。

- `dnf upgrade`をしても、今のリリースのカタログの中にある更新しか入らない
- 新しいリリースのカタログに移るには、明示的に指定する必要がある

```bash
# 新しいリリースがあるか確認する
dnf check-release-update

# 新しいリリースに移る（2023.x.yは、上のコマンドで表示されたバージョンに置き換える）
sudo dnf upgrade --releasever=2023.x.y
```

カタログを固定する理由は、**同じAMIから起動したサーバーなら、いつ`dnf install`しても同じバージョンが入る**ようにするためである。先週起動したサーバーと今日起動したサーバーで、入るPHPのバージョンが違う、ということが起きない。npmで言えば、**package-lock.jsonがサーバー全体に効いている**ようなものである。

その代わり、セキュリティ更新を取り込むときは「新しいリリースに移る」作業を自分で行う必要がある。

Amazon Linux 2にはこの仕組みはなく、常に最新のカタログを見る。なお、Amazon Linux 2は2026年6月30日でサポートが終了している。

## 8. ダウンロードしたものはどこに置かれるのか

### 実行したディレクトリに左右されるか

「dnfもaptもcurlもwgetも、置き場所が決まっている」と考えがちだが、**curlとwgetは決まっていない**。

| 道具 | どこに置かれるか | 実行したディレクトリに左右されるか |
| --- | --- | --- |
| dnf／apt（中身はrpm／dpkg） | **パッケージの中に書かれた絶対パス**（`/usr/bin/php`、`/etc/php.ini`など） | されない |
| `install`コマンド | **引数で指定した場所**（`/usr/local/bin/terraform`など） | されない（絶対パスで指定した場合） |
| curl -O／wget | **今いるディレクトリ** | **される** |
| npm install | 近くにある`package.json`のディレクトリの`node_modules` | **される** |
| npm install -g | npmのグローバルの置き場所（`npm prefix -g`で確認できる） | されない |

curlとwgetは①取得しかしないので、ファイルを**今いるディレクトリに保存するだけ**である。保存先は`-o`（curl）や`-P`（wget）で変えられる。

```bash
cd /tmp
wget https://releases.hashicorp.com/terraform/1.14.3/terraform_1.14.3_linux_amd64.zip
ls
# terraform_1.14.3_linux_amd64.zip   ← 今いる /tmp に置かれる
```

そのため、手作業で入れるときは「`/tmp`などでダウンロードして展開し、`install`で決まった場所に置く」という流れになる。**置き場所を決めるのは③配置の担当**で、①取得の道具は置き場所に関わらない。

dnfは実行するディレクトリに関係なく、パッケージに書かれた場所に置く。どこで`dnf install php`を実行しても、`/usr/bin/php`に置かれる。

### 置き場所の慣習

Linuxには、どの種類のファイルをどこに置くかの慣習がある（FHS：Filesystem Hierarchy Standardという標準にまとめられている）。手作業で入れるときに大事なのは、**dnfが管理する場所と、自分が管理する場所を分ける**ことである。

| 場所 | だれが置くか |
| --- | --- |
| `/usr/bin` | パッケージ管理（dnf／apt）が置く。**自分で触らない** |
| `/usr/local/bin` | 管理者が手作業で置く（Terraformを`install`で置くならここ） |
| `/opt` | 1つのソフトウェアをディレクトリごと置く（一部の配布物） |
| `~/.local/bin` | sudoを使わず、自分のユーザーだけで使うとき |

手作業のものを`/usr/bin`に置くと、あとでdnfが同じ名前のファイルを置こうとしたときに上書きされたり、rpmの台帳と実際のファイルが食い違ったりする。`/usr/local/bin`に置けば、dnfとぶつからない。

`PATH`では`/usr/local/bin`が`/usr/bin`より前にあるので、同じ名前のコマンドが両方にあると、`/usr/local/bin`のほうが使われる。どちらが使われているかは`which terraform`で確認できる。

## 9. curlとwget

### 違い

どちらも①取得の道具である。違いは、何を得意としているかである。

| | curl | wget |
| --- | --- | --- |
| 何もオプションを付けないと | 中身を**画面（標準出力）に出す** | **ファイルとして保存する** |
| ファイルに保存するには | `-O`（URLの名前で保存）または`-o 名前` | そのままでよい |
| 得意なこと | APIを呼ぶ（`-X POST`、`-H`、`-d`）。HTTP以外の多くのプロトコルにも対応 | 大きなファイルの取得、途中からの再開（`-c`）、サイトを丸ごと取得（`-r`） |
| リダイレクト | `-L`を付けないとたどらない（GitHub Releasesなどでは必須） | 自動でたどる |
| 入っているか | Amazon Linux 2023にもUbuntuにも最初から入っている | Amazon Linux 2023の最小構成には入っていないことがある（`dnf install wget`で入れる） |

一言でまとめると、**curlは「HTTPで話すための道具」、wgetは「ファイルを取ってくるための道具」**である。

```bash
# 同じファイルを取ってくる
curl -LO https://releases.hashicorp.com/terraform/1.14.3/terraform_1.14.3_linux_amd64.zip
wget https://releases.hashicorp.com/terraform/1.14.3/terraform_1.14.3_linux_amd64.zip

# curl が得意なこと：APIを呼ぶ
curl -X POST -H 'Content-Type: application/json' -d '{"name":"test"}' https://api.example.com/items
```

### なぜdnfやaptではなくcurlやwgetを使うことがあるのか

主な理由は次の3つである。

- **リポジトリにない**：Terraformのように、標準のリポジトリに入っていないソフトウェアがある
- **リポジトリの版が古い**：リポジトリのものは検証を経てから入るので、最新版が出てもすぐには入らない。最新版がすぐ欲しいときは、配布元から直接取る
- **パッケージではない**：設定ファイルやデータ、インストール用のスクリプトなど、そもそもパッケージになっていないものを取ってくる

ただし、curlやwgetは①取得しかしないので、dnfがやってくれていたことを自分でする必要がある。

| dnfがやってくれること | curl／wgetで入れるときに自分ですること |
| --- | --- |
| 依存関係の解決 | 必要なものを自分で調べて入れる（Terraformは1つの実行ファイルで完結しているので不要） |
| 署名の検証 | 配布元が公開しているチェックサム（`SHA256SUMS`など）と照らし合わせる |
| 配置 | `install`で決まった場所に置く |
| 記録・更新・削除 | 何を入れたかを自分で覚えておく。更新するときは同じ手順をやり直す。削除するときは自分で`rm`する |

### よく見る形：`curl … | bash`

インストール方法として、次の形をよく見かける（nvm、Docker、Homebrewなど）。

```bash
curl -fsSL https://example.com/install.sh | bash
```

これは、ダウンロードしたシェルスクリプトを、ファイルに保存せずにそのまま`bash`に渡して実行する形である。この場合、①〜④は**そのスクリプトが全部、自分の好きなように行う**。どこに何を置くか、何を書き換えるかは、スクリプトの中身次第である。

dnfは⑤でパッケージが配布元のものかを確認してくれるが、`curl | bash`は何も確認しない。中身を見ないまま`sudo`付きで実行すれば、配布元とダウンロード経路を全面的に信用していることになる。気になるときは、一度ファイルに保存して中身を読んでから実行する。

```bash
curl -fsSL -o install.sh https://example.com/install.sh
less install.sh      # 中身を確認する
bash install.sh
```

## 10. 展開（解凍）

curlやwgetで取ってきたものは、そのままでは使えず、展開が必要なことがよくある。配布物を圧縮してまとめるのは、**たくさんのファイルを1つにする**ためと、**ダウンロードするサイズを小さくする**ためである。

| 拡張子 | 中身 | 展開のコマンド |
| --- | --- | --- |
| `.tar.gz`（`.tgz`） | 複数のファイルを`tar`で1つにまとめ、`gzip`で圧縮したもの | `tar -xzf ファイル名` |
| `.tar.xz` | `tar`でまとめ、`xz`で圧縮したもの | `tar -xJf ファイル名` |
| `.zip` | まとめることと圧縮を1つの形式で行ったもの | `unzip ファイル名`（入っていなければ`dnf install unzip`） |
| `.gz`（`tar`なし） | 1つのファイルを圧縮しただけ | `gunzip ファイル名` |
| 拡張子なし | 実行ファイルがそのまま（kubectlなど） | 展開は不要 |

`tar -xzf`のオプションは、`x`＝展開する（extract）、`z`＝gzipを解く、`f`＝次の引数をファイル名として扱う、という意味である。

dnfで入れるときに展開を意識しないのは、`.rpm`ファイルの展開をrpmが中で行っているからである。`.rpm`も中身はファイルをまとめて圧縮したものなので、やっていることは`tar -xzf`と同じ②展開である。

### 展開しても元のファイルは変わらない

展開は、元のファイル（アーカイブ）を**読んで**、中に入っているファイルを**新しく書き出す**ことである。元のファイルを書き換えて展開後の形に変えるわけではない。展開が終わると、元のファイルと展開後のファイルが両方ある状態になる。

dnfで入れるときの`.rpm`も同じで、ファイルの形が変わるのではなく、置き場所ごとに別のファイルができる。

```
【リポジトリ】 Packages/php8.2-cli-….rpm
      │ ①取得：dnfがダウンロード（中身は変わらないコピー）
      ▼
【自分のサーバー】 /var/cache/dnf/の下に php8.2-cli-….rpm
      │ ②展開・③配置：rpmが.rpmを読み、中のファイルを新しく書き出す（.rpm自体は変わらない）
      ▼
/usr/bin/php など ＋ ④記録：台帳（/var/lib/rpm/）
      その後、dnfはキャッシュの.rpmを消す（keepcacheが既定のFalseの場合）
```

インストールした後に`.rpm`が手元に残らないのは、展開で`.rpm`が形を変えたからではない。dnfが**別の処理として消している**からである。dnfの設定の`keepcache`の既定値は`False`で、`True`にするとダウンロードした`.rpm`がキャッシュに残る（[dnfの設定のリファレンス](https://dnf.readthedocs.io/en/latest/conf_ref.html)で確かめた）。

手元のUbuntu 24.04で、展開の前後に元のファイルのハッシュ値（`sha256sum`）を比べて確かめた。この環境にはrpmが無いので、パッケージは同じ仕組みの`.deb`（`dpkg-deb -x`で展開）で試した。

| 展開のコマンド | 元のファイル | 確かめたバージョン |
| --- | --- | --- |
| `tar -xzf pkg.tar.gz` | 残る。ハッシュ値も変わらない | GNU tar 1.35 |
| `unzip pkg.zip` | 残る。ハッシュ値も変わらない | UnZip 6.00 |
| `dpkg-deb -x hello_….deb out` | 残る。ハッシュ値も変わらない | dpkg-deb 1.22.6 |
| `gunzip one.txt.gz` | **消える**（`one.txt`だけになる） | gzip 1.12 |
| `gunzip -k one.txt.gz` | 残る（`-k`＝`--keep`） | gzip 1.12 |

例外は`gzip`／`gunzip`である。1つのファイルを圧縮するだけの道具なので、圧縮や展開をすると**元のファイルを消して置き換える**。残したいときは`-k`を付ける。tarやunzipのように、複数のファイルをまとめたものを展開する道具は、元のファイルを残す。

## 11. 「install」という言葉の意味の違い

`install`という言葉は、**どのプログラムに渡された単語か**によって、意味がまったく違う。

| 書き方 | 実際に動いているもの | やること | 担当する段階 |
| --- | --- | --- | --- |
| `sudo install terraform /usr/local/bin/terraform` | coreutilsの`install`コマンド | ファイルのコピーと権限の設定 | ③ |
| `sudo make install` | Makefileに書かれた手順 | ソースからビルドしたものを配置する（中で`install`コマンドを呼ぶことが多い） | ③ |
| `sudo ./aws/install` | 配布物に入っている`install`という名前のスクリプト（AWS CLI v2） | スクリプトに書かれたとおりに配置する | ③ |
| `sudo dnf install php8.2` | dnfのサブコマンド | リポジトリから取得し、依存関係を解決して、配置・記録する | ①〜④ |
| `npm install` | npmのサブコマンド | レジストリから取得し、`node_modules`に配置して、`package-lock.json`に記録する | ①〜④ |

### `sudo`は`install`とは別のコマンド

`sudo install …`の`install`は、`sudo`のサブコマンドではない。`sudo`は、**後ろに続くコマンドをroot権限で実行する**だけのコマンドである。`sudo dnf install`も`sudo install`も、`sudo`がやっていることは同じで、違うのは後ろのコマンドである。

`sudo`が必要かどうかは、**書き込む場所の権限**で決まる。

| コマンド | 書き込む場所 | sudoが必要か |
| --- | --- | --- |
| `dnf install` | `/usr/bin`、`/etc`、rpmの台帳など | 必要 |
| `install … /usr/local/bin/` | `/usr/local/bin`（rootしか書き込めない） | 必要 |
| `install … ~/.local/bin/` | 自分のホームディレクトリ | 不要 |
| `wget`（`/tmp`などで実行） | 今いるディレクトリ | 不要 |
| `npm install` | 今いるプロジェクトの`node_modules` | 不要 |

### coreutilsの`install`コマンド

`install`は、`cp`や`mv`と同じcoreutils（Linuxの基本コマンドのセット）に入っているコマンドである。**ファイルをコピーし、同時に権限と所有者を設定する**だけで、何もダウンロードしない。

`sudo install terraform /usr/local/bin/terraform`には権限の指定がないが、`install`には次の決まりがある。

| 項目 | 指定を省略したとき | `sudo install terraform /usr/local/bin/terraform`の場合 |
| --- | --- | --- |
| 権限（`-m`） | `0755`（持ち主は読み・書き・実行、それ以外は読み・実行） | `rwxr-xr-x` |
| 所有者（`-o`） | 実行したユーザー | sudoで実行しているので`root` |
| グループ（`-g`） | 実行したユーザーのグループ | `root` |

```bash
ls -l /usr/local/bin/terraform
# -rwxr-xr-x 1 root root ... /usr/local/bin/terraform
```

`install`が`0755`を基本にしているのは、**実行ファイルを配置するための道具**として作られたからである。`cp`と比べると違いがわかる。

- `cp`で新しくファイルを作ると、コピー元の権限からumaskの分を除いた権限になる
- `install`は、コピー元の権限に関係なく、**毎回決まった権限（指定がなければ0755）にそろえる**。umaskの影響も受けない

展開したファイルに実行権限が付いていなくても、`install`を通せば「全員が実行できて、rootしか書き換えられない」状態で置かれる。`cp`、`chmod 755`、`chown root:root`の3つを1回で済ませられる、というのが`install`を使う理由である。

## 12. 通し例：Terraformを2通りで入れる

ここまでの内容を、Terraformを入れる2つの方法で確かめる。

### A. wgetで取ってきて手作業で入れる

```bash
cd /tmp

# ①取得：本体と、チェックサムの一覧を取ってくる
wget https://releases.hashicorp.com/terraform/1.14.3/terraform_1.14.3_linux_amd64.zip
wget https://releases.hashicorp.com/terraform/1.14.3/terraform_1.14.3_SHA256SUMS

# （署名の検証の代わり）ダウンロードしたファイルが、公開されているチェックサムと一致するか確認する
sha256sum --check --ignore-missing terraform_1.14.3_SHA256SUMS
# terraform_1.14.3_linux_amd64.zip: OK

# ②展開
unzip terraform_1.14.3_linux_amd64.zip

# ③配置：PATHが通っていて、dnfとぶつからない /usr/local/bin に置く
sudo install terraform /usr/local/bin/terraform

# 確認
terraform version
which terraform
# /usr/local/bin/terraform

# ④記録：誰もしていない
rpm -qf /usr/local/bin/terraform
# file /usr/local/bin/terraform is not owned by any package
```

チェックサムの確認でわかるのは、「ダウンロードしたファイルが`SHA256SUMS`に書かれたものと同じ」ということだけである。`SHA256SUMS`自体が本物かどうかまで確かめるには、HashiCorpが公開している署名（`SHA256SUMS.sig`）を公開鍵で検証する必要がある。dnfの⑤は、この作業を自動で行っている。

### B. リポジトリを追加してdnfで入れる

```bash
# ①のリポジトリの設定ファイルを1つ増やす
sudo dnf config-manager --add-repo https://rpm.releases.hashicorp.com/AmazonLinux/hashicorp.repo
ls /etc/yum.repos.d/
# amazonlinux.repo  hashicorp.repo  kernel-livepatch.repo   ← 増えている

# あとは PHP と同じように入れられる
sudo dnf install terraform

# ④記録が残っている
rpm -qf /usr/bin/terraform
# terraform-1.14.x-1.x86_64
```

リポジトリを追加するとは、**6章の①の設定ファイルを1つ増やすこと**である。これだけで、dnfはHashiCorpのカタログも見るようになり、`dnf install terraform`がURLなしで動くようになる。

コマンドの細かい部分は変わることがあるので、実際に作業するときはHashiCorpの公式のインストール手順を確認すること。

### AとBの比較（＋dnfで入れたPHP）

| | A. wget＋installのTerraform | B. dnfのTerraform | dnfのPHP |
| --- | --- | --- | --- |
| 取得元 | HashiCorpのサイト（URLを自分で指定） | HashiCorpのリポジトリ（追加した設定ファイルに書いてある） | Amazon Linuxのリポジトリ（最初から設定ファイルに書いてある） |
| 配布元の確認 | チェックサムを自分で確認 | GPG署名をdnfが自動で検証 | GPG署名をdnfが自動で検証 |
| 置き場所 | `/usr/local/bin`（自分で決めた） | `/usr/bin`（パッケージが決めている） | `/usr/bin`（パッケージが決めている） |
| 台帳の記録 | 残らない | 残る | 残る |
| 更新 | 同じ手順をやり直す | `dnf upgrade terraform` | `dnf upgrade`（Amazon Linux 2023ではリリースの固定に注意） |
| 削除 | `sudo rm /usr/local/bin/terraform` | `dnf remove terraform` | `dnf remove php8.2` |
| 向いている場面 | 決まったバージョンを確実に入れたい。リポジトリを増やしたくない | 複数台で同じ管理をしたい。更新を楽にしたい | OSが用意しているものを使う |

## 13. まとめ

| 疑問 | 答え |
| --- | --- |
| dnfとaptの違いは？ | ディストリビューションの系統の違い。Red Hat系（Amazon Linuxなど）は`.rpm`とdnf、Debian系（Ubuntuなど）は`.deb`とapt |
| rpm／dpkgとdnf／aptの違いは？ | rpm／dpkgは手元のパッケージを展開・配置・記録する低レベルの道具。dnf／aptはリポジトリから取得して依存関係を解決し、rpm／dpkgを呼ぶ高レベルの道具 |
| URLを指定しなくてよいのはなぜ？ | `/etc/yum.repos.d/`などのリポジトリの設定ファイルに、前もってURLが書いてあるから |
| npmと同じようなもの？ | 同じ。npmにも最初からレジストリのURLが設定されている |
| 「ダウンロードできるもののリスト」は？ | カタログ（メタデータ／パッケージリスト）。package.jsonは「欲しいもののリスト」で、別のもの |
| カタログを更新するコマンドは？ | aptは`apt update`。dnfは期限が切れたら自動で更新される（手動なら`dnf makecache`）。npmは手元に持たないので不要 |
| Amazon Linuxのカタログの固定とは？ | Amazon Linux 2023では、カタログが起動したときのリリースのバージョンに固定される。新しいリリースに移るには`--releasever`で明示する。Amazon Linux 2にはこの仕組みはない |
| curl／wgetを使うのはなぜ？ | リポジトリにない、リポジトリの版が古い、パッケージではない、のいずれか |
| curlとwgetの違いは？ | curlはHTTPで話す道具（標準では画面に出す。APIを呼ぶのが得意）。wgetはファイルを取ってくる道具（標準でファイルに保存する） |
| どのディレクトリで実行しても同じ？ | dnf／aptは同じ（パッケージに書かれた場所に置く）。**curl／wgetは今いるディレクトリに保存する**。npmもプロジェクトのディレクトリに置く |
| ダウンロードとインストールは別？ | 別。ダウンロードは手元に持ってくるだけ。インストールは使える状態に配置する（＋記録する）こと |
| `sudo install`は何をしている？ | coreutilsの`install`コマンドを、`sudo`でroot権限で実行している。コピーと権限の設定だけで、ダウンロードはしない。権限を省略すると`0755` |
| 「install」の意味は同じ？ | 違う。`install`コマンドは③配置だけ。`dnf install`／`apt install`／`npm install`は①〜④を全部行う |
| 解凍が必要なものは？ | `.tar.gz`、`.zip`などで配布されているもの。dnfは`.rpm`の展開を中で行っているので意識しないだけ |
| 展開すると元のファイルはどうなる？ | 変わらない。展開は中身を新しく書き出すこと。インストール後に`.rpm`が無くなるのは、dnfが別の処理として消すから（`keepcache`の既定が`False`）。`gunzip`だけは元のファイルを消す（`-k`で残せる） |
