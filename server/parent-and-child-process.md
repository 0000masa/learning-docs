# 親プロセスと子プロセス — プロセスは必ず別のプロセスから生まれる

「子プロセスとは何か？タスクマネージャーを見ても、あるプロセスの親がどれなのか分からない」という疑問に答えるノート。結論を先に言うと：

- **子プロセスは「あるプロセスが起動した、別のプロセス」。** 起動した側を親プロセスと呼ぶ。プロセスは必ず既にあるプロセスから作られるので、**すべてのプロセスに親がいる**（1章）。
- **子は親とメモリを共有しない。** 別のプロセスだから。受け継ぐのは環境変数や実行ユーザーなど、起動時の設定の写しだけ。ここがスレッドとの違い（2章）。
- **実行ユーザーを切り替えられるのはrootだけ。** すべてのプロセスはrootのPID 1から始まり、途中で一般ユーザーに切り替わっている。`sudo`も例外ではなく、rootとして動く`sudo`が子をrootで起動している（2章）。
- **タスクマネージャーでは親子関係が見えない。**「詳細」タブに親のPIDの列が無い。WindowsならProcess ExplorerかPowerShell、Linuxなら`ps -ef --forest`や`pstree`で見る（3章）。
- **親が先に終わったときの扱いが、LinuxとWindowsで違う。** LinuxではPID 1が子を引き取る。Windowsでは誰も引き取らない（4章）。

プロセスそのものとスレッドの話は → [process-and-thread.md](./process-and-thread.md)

## 0. どこで出てきたか

[process-and-thread.md](./process-and-thread.md)の3章で、開発用の`worker`コンテナにJavaのプロセスが3つ、親子の関係で並んでいた。5章では「子プロセスが落ちてもECSは気づかない」「親を失ったプロセスはPID 1に引き取られる」という話が出た。ここから「そもそも子プロセスとは何か」「親はどこで確かめられるのか」という疑問が出た。

## 1. 子プロセスとは

**あるプロセスがOSに頼んで起動させた、別のプロセス**のこと。頼んだ側が**親プロセス**、起動された側が**子プロセス**である。

プロセスは、何もないところからは生まれない。必ず既にあるどれかのプロセスが「このプログラムを起動して」とOSに頼んで作られる。そのため、すべてのプロセスに親がいる。親のPIDを**PPID**と呼ぶ。

身近な例：

| 親 | 子 | 何が起きているか |
|---|---|---|
| ターミナルのシェル（`bash`） | `ls` | `ls`と打つと、シェルが`ls`を子プロセスとして起動し、終わるのを待つ |
| エクスプローラー（`explorer.exe`） | ダブルクリックしたアプリ | Windowsでアプリを起動すると、エクスプローラーが親になる |
| `gradlew` | Gradleデーモン → アプリ本体 | 開発用の`backend` / `worker`コンテナ。3世代の親子（下の図） |
| Nginxのmaster | worker | masterがworkerを複数起動する（→ [process-models-by-server.md](./process-models-by-server.md)） |

開発用の`worker`コンテナを、もう一度見る。

```
$ docker compose exec worker ps -eo pid,ppid,args
    PID    PPID COMMAND
      1       0 java ... gradlew
     41       1 java ... (Gradle デーモン)
    140      41 java ... (アプリ本体)
    520       0 ps -eo pid,ppid,args
```

`PPID`の列を親の`PID`に結ぶと、1本の木になる。

```
PID 1    gradlew
└─ PID 41   Gradle デーモン      (PPID 1   = gradlew の子)
   └─ PID 140  アプリ本体         (PPID 41  = Gradle デーモンの子)
```

最後の行の`ps`自身はPPIDが0になっている。`docker compose exec`で起動したプロセスの親は、コンテナの外にいるDockerのプロセスである。コンテナの中からは外のプロセスが見えないので、0と表示される。PID 1のPPIDが0なのも同じ理由である。

### Linux全体では1本の木

Linuxでは、OSが起動して最初に作るプロセス（`systemd`、PID 1）が、すべてのプロセスの根になる。`systemd`が`sshd`を起動し、`sshd`がSSHで入ってきた人のシェルを起動し、シェルが`ls`を起動する、というように、全プロセスが1本の木にぶら下がっている。

```
systemd(PID 1)
├─ sshd
│  └─ sshd(接続ごと)
│     └─ bash
│        └─ ls
└─ containerd
   └─ containerd-shim
      └─ java(コンテナの PID 1)
```

## 2. 子が親から受け継ぐもの、受け継がないもの

子プロセスは**別のプロセス**なので、メモリ空間は親とは別になる。親が持っているオブジェクトや変数を、子が直接読むことはできない。同じプロセスの中でメモリを共有する**スレッドとは、ここが違う**。

| | 子プロセス | スレッド |
|---|---|---|
| 作った側とメモリを共有するか | **しない** | する |
| 作った側が終わったら | 生き残れる（4章） | プロセスごと終わる |
| PID | 自分のPIDを持つ | 持たない（プロセスのPIDに属する） |

子が親から受け継ぐのは、**起動したときの設定の写し**である。

| 受け継ぐもの | 補足 |
|---|---|
| 環境変数 | 親の環境変数の**写し**。子が書き換えても親には影響しない。環境変数の話は別ノート（未作成） |
| 実行ユーザー | 親と同じユーザー・権限で動く。切り替えられるのはrootだけ（次の節） |
| 作業ディレクトリ | 親がいたディレクトリから始まる |
| 標準入力・標準出力 | 親の画面やパイプにつながったまま。シェルから起動したコマンドの出力が、同じ画面に出るのはこのため |

コンテナでも同じで、`gradlew`に渡した環境変数（`APP_ROLE=worker`など）は、写しとしてGradleデーモン、アプリ本体へと受け継がれていく。

### 実行ユーザーは変えられるのか

変えられる。ただし、**変えられるのはrootだけ**である。実行ユーザーとファイルの権限の話は別ノート（未作成）で扱うが、原則は1つで、次のとおりである。

> **プロセスの実行ユーザーは、親からそのまま引き継がれる。それを変えられるのはrootだけ。**

一般ユーザーのプロセスは、自分の子を別のユーザーで動かすことはできない。実際に切り替えている例は、どれも**rootの親が、子を一般ユーザーに切り替えて**いる。

| 起動のしかた | 何が起きているか |
|---|---|
| `sshd`がログインを受け付ける | `sshd`はrootで動いている。ログインが通ると子プロセスを作り、ログインした人のユーザーに切り替えてからシェルを起動する |
| systemdの`User=appuser` | rootのsystemdが子を作り、アプリを実行する直前に`appuser`に切り替える |
| Nginx / php-fpm | 親（master）はrootで起動して80番ポートを開き、子（worker）だけを`www-data`などに切り替える |
| このリポジトリの本番イメージ | `docker/app/Dockerfile`の`USER app`。コンテナを起動する側（root）が、`java`を`app`ユーザーで起動する |

切り替えは、普通は**権限を下げる**方向にだけ使う。一度下げた子は、rootに戻れない。Nginxのworkerが乗っ取られてもrootの権限を使えないのは、このためである。

### すべての系譜はrootから始まる

1章で見たとおり、すべてのプロセスはPID 1を根とする1本の木にぶら下がっている。そのPID 1は、OS（カーネル）が起動時に**rootとして**作る。したがって、**どのプロセスも、先祖をたどるとrootから始まり、途中のどこかで一般ユーザーに切り替わっている**。

このPC（WSL）で、Claude Codeから実行したコマンドの先祖をたどった（`pstree -s -u -p`。`-u`はユーザーが親と変わったところにユーザー名を書く）。

```
systemd(1)                     root
└─ init-systemd(Ubuntu)(2)     root
   └─ SessionLeader(1448)      root
      └─ Relay(1449)           root
         └─ bash(1453,masa)    ← ここで masa に切り替わる
            └─ claude(16349)   masa
               └─ bash(95808)  masa
                  └─ pstree    masa
```

WSLのrootのプロセス（`Relay`）が、子の`bash`を作るときに`masa`に切り替えている。それより下は、`masa`を引き継いでいるだけである。Linuxサーバーなら、この切り替えを`sshd`やログイン画面のプロセスが行う。

コンテナも同じである。コンテナの中のPID 1から見ると先祖は見えないが、ホストから見ればコンテナを起動する側（`containerd-shim`）はrootで、それが`USER app`に従って`app`に切り替えている。

### `sudo`は例外ではない

`sudo`は一般ユーザーのシェルから起動するので、一見「一般ユーザーがrootに上がっている」ように見える。実際には、**一般ユーザーのシェルはそのまま**で、**rootとして動く`sudo`が、子としてコマンドをrootで起動している**。

`sudo`がrootとして動けるのは、ファイルに**setuid**という印が付いているからである。この印があるプログラムは、起動した人ではなく**ファイルの持ち主（root）として**動く。`ls -l`すると、持ち主の実行権限の位置が`x`ではなく`s`になっている。

```
$ ls -l /usr/bin/sudo /usr/bin/passwd
-rwsr-xr-x 1 root root 282032 ... /usr/bin/sudo
-rwsr-xr-x 1 root root  64152 ... /usr/bin/passwd
```

`sudo apt update`と打つと、シェルが`sudo`を子プロセスとして起動し、実行したいコマンド（`apt update`）を引数として渡す。どこかで待ち構えている`sudo`に頼みに行くのではない。`sudo`は、**起動した瞬間からrootとして動いている**。

```
bash(masa)                       ← ずっと masa のまま
└─ sudo apt update(起動した瞬間から root。実ユーザーは masa)
   │ ① /etc/sudoers で、masa にこのコマンドが許されているか確かめる
   │ ② masa 自身のパスワードを確かめる(root のパスワードではない)
   └─ apt update(root。-u で指定すれば別のユーザー)
```

`/etc/sudoers`では、許すコマンドまで絞れる。パスワードは一度入れると、しばらく（既定で15分）聞かれない。

つまり「切り替えられるのはrootだけ」という原則は破れていない。rootとして動く`sudo`が、確認を済ませてから切り替えている。rootになるのは**そのコマンドと、その子孫だけ**で、終わればシェル（`masa`）に戻ってくる。`sudo -i`でrootのシェルに入ったように見えるときも、rootのシェルが`sudo`の子として起動されているだけである。

`passwd`（自分のパスワードを変えるコマンド）にもsetuidが付いている。パスワードを保存するファイル（`/etc/shadow`）はrootしか書き換えられないので、一般ユーザーが自分のパスワードを変えるには、rootとして動く`passwd`に頼むしかない。

### プロセスはuidを2つ持っている — 実ユーザーと実効ユーザー

rootとして動いている`sudo`が、なぜ「依頼したのは`masa`だ」と分かるのか。それは、**どのプロセスも、ユーザーを表すuidを最初から複数持っている**からである。

| | 中身 | 使い道 |
|---|---|---|
| **実ユーザー**（real uid） | そのプロセスを起動した人 | 「誰の依頼か」を表す |
| **実効ユーザー**（effective uid） | 権限の判定に使うuid | ファイルを読めるか、ユーザーを切り替えられるかなどは、こちらで判定される |

普通のプロセスでは、2つとも親から引き継いだ同じ値になっている。**setuidはuidを追加するものではない。** setuidの印が付いたファイルを起動したときだけ、**実効ユーザーがファイルの持ち主に置き換わり**、実ユーザーは起動した人のまま残る。`sudo`は、この実ユーザーを見て`/etc/sudoers`を引く。

このPCで確かめた。`/proc/<PID>/status`の`Uid:`の行は、左から実ユーザー、実効ユーザー、保存ユーザー（saved uid）、ファイルシステム用ユーザーの4つを並べている。保存ユーザーは「元の実効ユーザーを覚えておく」もので、残りの1つは実効ユーザーと同じ値になるのが普通である。`1000`は`masa`、`0`はrootのuidである。

```
# 普通のプロセス(grep 自身)。4 つとも masa
$ grep Uid /proc/self/status
Uid:    1000    1000    1000    1000

# setuid の付いた passwd を、masa が起動した(パスワード入力待ちの間に見た)
$ ps -o user,ruser,pid,comm -p <passwd の PID>
USER     RUSER        PID COMMAND
root     masa       99557 passwd
$ grep Uid /proc/<passwd の PID>/status
Uid:    1000    0       0       0
```

`passwd`は、実ユーザーが`masa`（1000）のまま、実効ユーザーがroot（0）になっている。`ps`の`USER`列は実効ユーザー、`RUSER`列は実ユーザーを表示する。`passwd`はこの実ユーザーを見て、「`masa`のパスワードだけを変えてよい」と判断する。

なお、プログラムの中からuidを切り替える命令（関数）も`setuid()`という名前である。ファイルの印のsetuidとは別物で、rootの親が子を一般ユーザーに切り替えるとき（`sshd`やNginx）に使うのは、こちらの関数である。

### Windowsでは

Windowsでも、子は親のユーザー（正確には**アクセストークン**）を引き継ぐ。切り替える手段は、次の2つである。

| 手段 | 何が起きるか |
|---|---|
| 右クリックの「別のユーザーとして実行」（`runas`） | そのユーザーのパスワードを入れると、そのユーザーとして子を起動する |
| 「管理者として実行」（UACの確認画面） | 同じユーザーのまま、管理者の権限を持ったトークンで子を起動する |

どちらもOSの確認を通してから切り替える仕組みで、プログラムが勝手にユーザーを変えることはできない。UACの確認画面は、Linuxの`sudo`のパスワード確認に近い役割である。

## 3. 親子関係の見方

### タスクマネージャーでは分からない

タスクマネージャーの「詳細」タブには、PIDの列はあるが、**親のPIDの列が無い**（「列の選択」にも無い）。

「プロセス」タブでChromeなどを展開すると、中身がまとまって見える。ただしこれは**アプリ単位のまとまり**で、親子関係そのものではない。

### 見る方法

| 環境 | 方法 | 見え方 |
|---|---|---|
| Windows | **Process Explorer**（Microsoft公式のSysinternalsツール。無料） | 親子が木の形で並ぶ。タスクマネージャーの代わりとしてよく使われる |
| Windows | PowerShellで`Get-CimInstance Win32_Process \| Select-Object ProcessId, ParentProcessId, Name` | `ParentProcessId`が親のPID |
| Linux | `ps -ef` | `PPID`の列が親のPID |
| Linux | `ps -ef --forest` / `pstree -p` | 親子を木の形で表示する |
| コンテナ | `docker compose exec <サービス> ps -eo pid,ppid,args` | コンテナの中の親子。外の親は0と表示される（1章） |

## 4. 親が先に終わったとき

親が子より先に終わったとき、残された子の扱いがOSによって違う。

| | Linux | Windows |
|---|---|---|
| 残された子 | **PID 1の子に付け替えられる**（PPIDが1になる） | 誰にも付け替えられない。**消えた親のPIDを記録したまま**動き続ける |
| 子が終わったとき | 新しい親（PID 1）が、終了を受け取って片付ける必要がある | 特に何も要らない |

Linuxで、親を失った子を引き取ることを**再親子付け**（reparenting）と呼ぶ。引き取ったPID 1が子の終了を受け取らない（`wait`しない）と、終わった子の記録が**ゾンビプロセス**として残り続ける。普通のLinuxでは`systemd`が片付けてくれるが、コンテナの中では、PID 1がアプリ本体（このリポジトリなら`java`）になる。アプリは片付けをしないので、ゾンビが溜まりうる。これが、ECSの`initProcessEnabled`でinitプロセスをPID 1に置く理由である（→ [process-and-thread.md](./process-and-thread.md)の5章）。

Windowsでは、記録された親のPIDが、後から起動した**別のプロセスに使い回されている**ことがある。Windowsで親子関係をたどるときは、親のPIDが本当にその親かどうか、起動時刻も合わせて確かめる必要がある。Process Explorerは、親が既に終わっている子を木の根の側に表示する。

### 親が終わると子も止まる、とは限らない

親が終わっても、子は自動では止まらない（Linux・Windowsとも）。ターミナルを閉じるとそこから起動したコマンドも止まるのは、親子だからではなく、ターミナルが閉じるときに子へ終了の合図（SIGHUP）を送っているからである。

同じように、コンテナのPID 1に届いたSIGTERMは、子プロセスには自動では届かない。PID 1が自分で子に伝える必要がある。シェルスクリプトから`exec`を付けずにアプリを起動すると、SIGTERMがアプリに届かないのはこのためである（→ [process-and-thread.md](./process-and-thread.md)の5章）。

## つまずきポイント

- **子プロセスを、スレッドと同じものだと思う。** 子プロセスは別のプロセスで、親とメモリを共有しない。受け継ぐのは起動時の設定の写しだけ（2章）
- **タスクマネージャーの「プロセス」タブのまとまりを、親子関係だと思う。** あれはアプリ単位のまとまり。親子はProcess ExplorerやPowerShellで見る（3章）
- **子が環境変数を書き換えれば、親にも伝わると思う。** 子が持っているのは写し。親には戻らない（2章）
- **`sudo`で、自分のシェルがrootになったと思う。** シェルは一般ユーザーのまま。rootになるのは`sudo`が起動したコマンドとその子孫だけ（2章）
- **一般ユーザーのプロセスでも、子を別のユーザーで動かせると思う。** 切り替えられるのはrootだけ。`sudo`や`passwd`はsetuidでrootとして動いているから切り替えられる（2章）
- **setuidを「uidを追加する仕組み」だと思う。** プロセスは最初から実ユーザーと実効ユーザーを持っている。setuidは、実効ユーザーをファイルの持ち主に置き換えるだけ（2章）
- **親が終われば子も終わると思う。** 子は自動では止まらない。ターミナルを閉じたときに止まるのは、ターミナルが合図を送っているから（4章）
- **コンテナの中でPPIDが0のプロセスを、親がいないプロセスだと思う。** 親はコンテナの外にいて、中から見えないだけ（1章）
- **Windowsで、PPIDが指すプロセスを親だと信じ切る。** 親が終わった後、そのPIDが別のプロセスに使い回されていることがある（4章）

## 用語集

- **親プロセス** — 別のプロセスを起動したプロセス
- **子プロセス** — 別のプロセスから起動されたプロセス。親とはメモリを共有しない
- **PPID** — 親プロセスのPID
- **プロセスツリー** — 親子関係でプロセスを結んだ木。Linuxでは`systemd`（PID 1）が根になる
- **再親子付け（reparenting）** — Linuxで、親を失ったプロセスをPID 1などが引き取ること
- **ゾンビプロセス** — 終了したのに、親がその終了を受け取らないため、記録だけが残っているプロセス
- **root** — Linuxの管理者ユーザー。プロセスの実行ユーザーを切り替えられる唯一のユーザー。PID 1はrootとして動く
- **setuid** — 実行ファイルに付ける印。起動すると、実効ユーザーがファイルの持ち主に置き換わる（実ユーザーは起動した人のまま）。`ls -l`で`rws`と表示される。uidを切り替える関数`setuid()`とは別物
- **実ユーザー（real uid）** — プロセスを起動した人。「誰の依頼か」を表す
- **実効ユーザー（effective uid）** — 権限の判定に使うuid。普通は実ユーザーと同じで、setuidのときだけ違う値になる
- **`sudo`** — setuidでrootとして動き、`/etc/sudoers`とパスワードを確かめてから、コマンドをroot（または指定したユーザー）で起動するコマンド
- **アクセストークン** — Windowsで、プロセスがどのユーザーとどの権限で動いているかを表すもの。子は親のトークンを引き継ぐ
- **UAC** — Windowsの「管理者として実行」の確認画面。管理者の権限を持ったトークンで子を起動する
- **Process Explorer** — MicrosoftのSysinternalsが配布する、プロセスを親子の木で表示するツール
- **`ps -ef --forest` / `pstree`** — Linuxで、プロセスを親子の木の形で表示するコマンド
