# プロセスとスレッド — 「メモリを分けるか、共有するか」の違い

「プロセスとはそもそも何か？タスクマネージャーで見えて、PIDで検索できるもの？Spring Bootは1つのプロセスの中で`http-nio-8080-exec-…`や`sqs-receiver-auth-mail`のスレッドを動かしているが、これらを別々のプロセスに分けることはできないのか？サーバーは1つのプロセスしか動かせないのか？」という疑問に答えるノート。結論を先に言うと：

- **プロセスは「実行中のプログラム1つ」。** OSが1つずつにPIDを振って管理する。タスクマネージャーの「詳細」タブや、Linuxの`ps`で見えるもの。**プロセスごとにメモリが分けられている**（1章）。
- **スレッドは「プロセスの中で、コードを順に実行していく流れ」。** 1つのプロセスの中に何本も持てて、**同じプロセスのスレッド同士はメモリを共有する**（2章）。
- **スレッドを、そのまま別のプロセスに移すことはできない。** スレッドが同じプロセスにいるのは、オブジェクトを共有するためだから。ただし**役割を別のプロセスに分ける**ことはできる。このリポジトリの`backend`と`worker`がそれで、2つのプロセスはメモリを共有できないので、依頼をSQS経由で渡している（4章）。
- **サーバーは1つのプロセスしか動かせない、ということはない。** OSの上では普段から数百のプロセスが動いている。「1つ」になりがちなのはコンテナのほうで、**1コンテナにつき主なプロセスは1つ**という慣習がある（5章）。

技術ごとのプロセスとスレッドの使い方（Spring Boot / Node.js / Laravel / Nginx / Apache）は別ノートにまとめた → [process-models-by-server.md](./process-models-by-server.md)

親プロセスと子プロセス、タスクマネージャーで親子関係を見る方法も別ノートにまとめた → [parent-and-child-process.md](./parent-and-child-process.md)

## 0. どこで出てきたか

あるSpring Bootアプリの`AuthMailQueueConfig`クラスにある`exit`メソッドは、`new Thread(...)`で`auth-mail-exit`というスレッドを作り、その中でSpringとJVMを終了させている。受信ループの`SqsReceiveLoop`クラスも、`sqs-receiver-auth-mail`という専用のスレッドで動いている。ここから「スレッドとは何か」「プロセスとはどう違うのか」という疑問が出た。

## 1. プロセスとは

**実行中のプログラム1つ**のこと。ディスクにある`java`や`node`のファイルは「プログラム」で、それを起動して動いている状態のものが「プロセス」。同じプログラムを2回起動すれば、プロセスは2つになる。

OSはプロセスごとに次のものを用意する。

| OSが用意するもの | 意味 |
|---|---|
| **PID**（プロセスID） | プロセスを見分ける番号。起動するたびに振られる |
| **専用のメモリ空間** | そのプロセスだけが読み書きできるメモリ。**別のプロセスのメモリは直接読めない** |
| 実行ユーザー | どの権限で動いているか。実行ユーザーの話は別ノート（未作成） |
| 開いているファイルや通信 | ファイル、ネットワークの接続など |
| 環境変数 | 起動時に渡された変数。環境変数の話は別ノート（未作成） |

### どこで見えるか

| 環境 | 見る方法 |
|---|---|
| Windows | タスクマネージャーの「詳細」タブ。PIDの列がある。列の見出しを右クリックして「列の選択」から「スレッド」を足すと、プロセスごとのスレッド数も見える |
| Linux / Mac | `ps -ef`（一覧）、`top`（使用率の多い順に更新し続ける） |
| コンテナ | `docker compose exec <サービス> ps -ef`（コンテナの中）、`docker compose top`（ホストから見た一覧） |

## 2. スレッドとは

**プロセスの中で、コードを上から順に実行していく流れ**のこと。1つのプロセスは、少なくとも1本のスレッドを持つ。必要なら何本でも足せる。

例えるなら、プロセスが**厨房**、スレッドがそこで働く**料理人**である。

- 料理人（スレッド）は、それぞれ別の料理（処理）を同時に進める
- 冷蔵庫（メモリ上のオブジェクト）は、同じ厨房の料理人全員で共有する
- 別の厨房（別のプロセス）の冷蔵庫には、手が届かない

### プロセスとスレッドの違い

| | プロセス | スレッド |
|---|---|---|
| メモリ | **プロセスごとに別々** | **同じプロセスのスレッド同士で共有** |
| データの受け渡し | 通信が要る（ネットワーク、ファイル、キューなど） | 同じオブジェクトを読み書きするだけ |
| 1つが落ちたとき | 他のプロセスは無事 | **同じプロセスごと落ちることがある**（メモリ不足など） |
| 作る手間 | 重い（メモリ空間を丸ごと用意する） | 軽い |
| 同時に書き換えたときの事故 | 起きない（共有していないので） | 起きる。`volatile`や`synchronized`で守る必要がある |

最後の行が、`SqsReceiveLoop`で`running`フィールドに`volatile`を付けたり、`synchronized (lock)`で囲んだりしている理由である。受信スレッドと終了処理のスレッドが、同じ`running`を読み書きするからだ。

### なぜスレッドを分けるのか

同時に進めたい仕事があるからである。受信ループは`receiveMessage`で最大20秒待つことを、ずっと繰り返す。これを起動処理と同じスレッドで実行すると、ループから抜けられず、起動がいつまでも終わらない。専用のスレッドに任せれば、起動処理は先に進み、受信は裏で続く。

HTTPも同じで、Tomcatはリクエストごとに別のスレッドを割り当てる。1本のスレッドで順番に処理すると、遅いリクエストが1つあるだけで、後ろのリクエストが全部待たされる。

## 3. 実測 — このリポジトリのコンテナの中を見る

開発環境の`worker`コンテナの中で`ps`を実行した（行は一部省略。`NLWP`はそのプロセスのスレッド数）。

```
$ docker compose exec worker ps -eo pid,ppid,nlwp,args
    PID    PPID NLWP COMMAND
      1       0   25 java ... -jar /app/gradle/wrapper/gradle-wrapper.jar bootRun --project-cache-dir /tmp/gradle-project-cache
     41       1   83 java ... (Gradle デーモン)
    138      41   57 java -XX:TieredStopAtLevel=1 ... -cp /app/build/classes/java/main:...
```

`jcmd -l`で、それぞれのJavaプロセスが何かを確かめた。

```
$ docker compose exec worker jcmd -l
1 /app/gradle/wrapper/gradle-wrapper.jar bootRun --project-cache-dir /tmp/gradle-project-cache
41 org.gradle.launcher.daemon.bootstrap.GradleDaemon 9.5.1
138 com.example.app.Application
```

### 1つのコンテナにJavaのプロセスが3つある

開発環境では、アプリを`./gradlew bootRun`で起動している（`docker/backend/Dockerfile`の`CMD`）。そのため、3つのプロセスが親子の関係で並ぶ。`PPID`は親プロセスのPIDである（親子関係そのものは → [parent-and-child-process.md](./parent-and-child-process.md)）。

```
PID 1    gradlew(Gradle を起動するだけの小さな Java)
└─ PID 41   Gradle デーモン(ビルドを実行する)
   └─ PID 138  アプリ本体(com.example.app.Application)
```

本番のイメージ（`docker/app/Dockerfile`）は`exec java -jar /app/app.jar`でjarを直接起動するので、Javaのプロセスはアプリ本体の1つだけになる。`exec`は、`sh`のプロセスを`java`に置き換える命令で、`sh`が親として残らない。

### 1つのプロセスの中のスレッド

アプリ本体（PID 138）のスレッドを`jstack`で取り出し、名前ごとに数えた（主なものだけ）。

```
$ docker compose exec worker sh -c "jstack 138 | grep '^\"'"
```

| スレッド名 | 本数 | 何をしているか |
|---|---|---|
| `http-nio-8080-exec-N` | 10 | Tomcatの、HTTPリクエストを処理するスレッド |
| `http-nio-8080-Acceptor` / `-Poller` | 1 / 1 | Tomcatの、接続を受け付けて処理するスレッドに振り分けるスレッド |
| `sqs-receiver-auth-mail` | 1 | 認証メールの受信ループ（`SqsReceiveLoop`の`start()`で作られる） |
| `sdk-ScheduledExecutor-N` | 5 | AWS SDKが、通信のタイムアウトなどを見張るスレッド |
| `lettuce-nioEventLoop-N` | 2 | Redisの通信（Spring Session） |
| `GC Thread#N`など | 多数 | JVM自身のスレッド（ガベージコレクション、コンパイルなど） |
| `DestroyJavaVM` | 1 | 後述 |

`/proc/138/status`で見たスレッド数は58本だった。1つのプロセスの中に、これだけのスレッドが同時に存在している。

`http-nio-8080-exec`が10本なのは、Spring Bootの既定値（`server.tomcat.threads.min-spare` = 10）のとおり。混んでくると最大200本（`server.tomcat.threads.max`）まで増える。

### `backend`には受信ループのスレッドが無い

同じことを`backend`コンテナのアプリ本体で行うと、`sqs-receiver-auth-mail`が**無い**。

| スレッド | `backend`（`APP_ROLE`未設定 = web） | `worker`（`APP_ROLE=worker`） |
|---|---|---|
| `http-nio-8080-exec-N` | 10 | 10 |
| `sqs-receiver-auth-mail` | **無い** | 1 |

同じソースから起動していても、`APP_ROLE=worker`のときだけ`AuthMailQueueConfig`が読み込まれ、受信ループのスレッドが作られる。設定の違いが、スレッドの有無として見えている。

### `main`スレッドはもう無い

一覧に`main`という名前のスレッドは無い。`main`スレッドは`main()`メソッドを実行するスレッドで、Spring Bootでは`SpringApplication.run(...)`が起動を終えて戻ると、`main()`も終わり、`main`スレッドも終わる。

それでもプロセスが終わらないのは、Tomcatなどの**デーモンでない**スレッドが残っているからである。JVMは、デーモンでないスレッドが1本でも動いている間は終了しない。`DestroyJavaVM`は、`main`が終わった後、それらが全部終わるのを待ってJVMを片付けるためのスレッドである。

### ホストから見ると、PIDが違う

ホスト側から`docker compose top`で見ると、同じプロセスに別のPIDが付いている。

```
$ docker compose top backend worker
SERVICE  PID    PPID   CMD
backend  1430   1407   java ... gradle-wrapper.jar bootRun
backend  1669   1430   java ... (Gradle デーモン)
backend  2103   1669   java ... (アプリ本体)
worker   1537   1481   java ... gradle-wrapper.jar bootRun --project-cache-dir /tmp/gradle-project-cache
worker   1715   1537   java ... (Gradle デーモン)
worker   2072   1715   java ... (アプリ本体)
```

コンテナは、中のプロセスに**別のPIDの番号体系**（PID名前空間）を見せている。コンテナの中では自分がPID 1から始まるように見えるが、ホストから見れば、どれも1台のOSの上で動く普通のプロセスである。`backend`のアプリ本体（ホストのPID 2103）と`worker`のアプリ本体（ホストのPID 2072）は、**別々のプロセス**だと分かる。

## 4. スレッドを別のプロセスに分けられるか

### スレッドをそのまま移すことはできない

スレッドが同じプロセスにいるのは、**オブジェクトを共有するため**である。たとえば`sqs-receiver-auth-mail`スレッドは、Springが作った`AuthMailWorker`や`SqsClient`のBeanを使って処理している。これらのBeanは、そのプロセスのメモリの中にある。別のプロセスに移ったら、そのメモリには手が届かない。

### 役割を別のプロセスに分けることはできる

できる。分けた側では、必要なオブジェクトを**自分のプロセスで作り直す**ことになる。このリポジトリが、まさにそうしている。

```
[backend プロセス]                        [worker プロセス]
 http-nio-8080-exec-N                      sqs-receiver-auth-mail
 (登録を受ける)                             (認証メールを送る)
   │                                           ▲
   │ メモリは共有できないので、                    │
   └──── JSON にして SQS に送る ──── SQS ────────┘
```

- `backend`と`worker`は**同じソースから起動した、別々のJVMプロセス**。Beanはそれぞれのプロセスで1セットずつ作られる
- プロセス同士はメモリを共有できないので、依頼はJSONの文字列にして、プロセスの外（SQS）を経由して渡す。受け取った側は、JSONから`AuthMailRequestedEvent`を作り直す

同じプロセスの中なら、オブジェクトをそのまま渡せば済む。SQSを経由するように変える前は、実際にそうしていた。

### 分けると何が良くなるか

| | 1つのプロセス | 別々のプロセス |
|---|---|---|
| 片方の障害 | メモリ不足などで、プロセスごと両方止まる | もう片方は動き続ける |
| 片方だけ止める・増やす | できない | できる（`docker compose stop worker`、ECSでワーカーだけ台数を増やす） |
| データの受け渡し | オブジェクトを渡すだけ | JSONにして、外部（SQS）を経由する必要がある |
| 二重に必要になるもの | 無い | DBの接続プール、メモリなどがプロセスの数だけ要る |

設計としては、認証メールの送信を`backend`の中で行わず、SQSを経由して`worker`に任せると決めた。

## 5. サーバーは1つのプロセスしか動かせないのか

### OSは数百のプロセスを同時に動かす

1台のサーバー（OS）の上では、普段から多数のプロセスが動いている。Linuxなら、`systemd`（他のプロセスを起動・管理する親玉）、`sshd`（SSHの受付）、ログの収集などである。アプリのプロセスは、その中の1つにすぎない。`ps -ef | wc -l`で数えると、何もしていないサーバーでも数十〜数百の行が出る。

CPUのコアが4つなら、ある瞬間に**本当に同時に**実行できるのは4本のスレッドまでである。それ以上のスレッドは、OSがごく短い時間で切り替えながら順に実行していて、人間には同時に動いているように見える。

この4本は、**同じプロセスのスレッドでなくてよい。** OSがCPUに載せる単位はスレッドで、どのプロセスのスレッドをどのコアで動かすかは、OS（スケジューラ）が決める。ある瞬間を切り取ると、たとえば次のようになっている。

```
コア 0: backend プロセスの http-nio-8080-exec-3
コア 1: worker プロセスの sqs-receiver-auth-mail
コア 2: MySQL プロセスのスレッド
コア 3: sshd プロセスのスレッド
```

次の瞬間には、それぞれのコアが別のスレッドに切り替わっている。別のプロセスのスレッドに切り替えるときは、メモリ空間も切り替えるので、同じプロセスのスレッド同士で切り替えるより少し重い。

### 「4コア8スレッド」のCPU

ハイパースレッディング（SMT）のあるCPUは、「4コア8スレッド」のように書かれる。ここで言う「スレッド」は、ハードウェア側のスレッド（**論理プロセッサ**）のことで、この章で扱ってきたソフトウェアのスレッドとは別物である。論理プロセッサは、ソフトウェアのスレッドを載せる**座席**にあたる。OSは、数千本あるソフトウェアのスレッドを、この座席に順番に載せて実行する。Windowsのタスクマネージャーの「パフォーマンス」タブにある「論理プロセッサ数」が、座席の数である。

SMTは、コアの中の**計算する部品（演算器など）は1組のまま**、**どこまで実行したかの記録（レジスタなど）を2組にした**ものである。1本のスレッドがメモリからデータが届くのを待っている間、計算する部品は遊んでしまう。その隙間に、もう1本の命令をハードウェアが流し込む。OSが数ミリ秒ごとに入れ替えるのとは違い、ハードウェアが1サイクル単位で2本の命令を混ぜて流すので、2本は本当に同時に実行中である。

ただし、計算する部品は2本で取り合うので、速さは2倍にはならない。一般に1.2〜1.3倍程度で、メモリ待ちの多い処理ほど伸び、計算ばかりする処理ではほとんど伸びない。まとめると、4コア8スレッドのCPUは次のようになる。

- **同時に実行中のスレッド**：8本
- **計算する力**：4コアぶん + α（8コアぶんではない）

### コンテナは「主なプロセス1つ」が慣習

1つのコンテナでは、主なプロセスを1つだけ動かすのがDockerの慣習である（コンテナの中のPID 1）。PID 1が終わると、コンテナも止まる。

ただしこれは慣習で、制限ではない。3章で見たとおり、開発用の`backend`コンテナの中にはJavaのプロセスが3つある。VS CodeのDev Containerで接続すると、VS Codeのサーバーのプロセスも中に増える。本番のイメージが`exec java -jar ...`でアプリ本体だけをPID 1にしているのは、ECSの停止の合図（SIGTERM）を、アプリが直接受け取れるようにするためでもある。

### ECSでも同じ慣習

ECSも、コンテナの中の**PID 1しか見ていない**。

| ECSがすること | 見ている相手 |
|---|---|
| コンテナが止まったか判断する（止まればタスクを入れ替える） | PID 1が終了したかどうか |
| 停止の合図SIGTERMを送る | PID 1だけ。`stopTimeout`（既定30秒）待っても終わらなければSIGKILL |
| ログをCloudWatch Logsに送る（`awslogs`） | コンテナの標準出力・標準エラー |

そのため、1つのコンテナで子プロセスを2つ動かすと困ったことが起きる。片方が落ちても、PID 1が生きていればECSは気づかない。SIGTERMも、子プロセスまで届くとは限らない。

複数のプロセスを一緒に動かしたいときは、プロセスごとに別のコンテナにして、1つのタスク定義の`ContainerDefinitions`に並べる。これを**サイドカー**と呼ぶ。ログ転送のFireLens（Fluent Bit）、CloudWatchエージェント、Service Connectのプロキシ（Envoy。ECSが自動で足す）などがこの形である。同じタスクのコンテナ同士は、`awsvpc`なら`localhost`で通信でき、ボリュームも共有できる。`Essential: true`を付けたコンテナが止まると、タスクごと止まる。

このリポジトリのタスク定義（`cloudformation/app.yml`の`app` / `migrate` / `mysql`）は、どれもコンテナが1つだけである。

### ECSでも、1つのコンテナに複数のプロセスが動くことはある

慣習は「**主な**プロセスを1つにする」ことで、補助のプロセスまで禁じてはいない。

| 例 | 中身 |
|---|---|
| ECS Exec | `EnableExecuteCommand: true`にすると、ECSがSSMエージェントをコンテナに差し込み、**コンテナの中のプロセスとして**動かす。`aws ecs execute-command`で入ったシェルも、そのコンテナの中のプロセスになる |
| シェルスクリプトから起動する | `sh start.sh`の中で`exec`を付けずに`java`を起動すると、`sh`がPID 1のまま残り、`java`はその子プロセスになる。SIGTERMが`java`に届かない原因になる |
| `initProcessEnabled` | 小さなinitプロセスがPID 1になり、アプリはその子プロセスになる（次の節） |
| supervisordでnginx + php-fpmをまとめる | 昔のLaravelのイメージでよく見る形。動くが、片方が落ちてもECSが気づかない |

このリポジトリでは、webサービスに`EnableExecuteCommand: true`が付いている（`cloudformation/app.yml`の`Service`）。そのため本番の`app`コンテナの中では、アプリの`java`（PID 1）のほかに、SSMエージェントのプロセスも動いている。

### `initProcessEnabled` — PID 1の仕事をinitに任せる

タスク定義のコンテナに付ける設定で、`docker run --init`と同じものである。有効にすると、コンテナの中で**tiniという小さなinitプロセスがPID 1になり**、`ENTRYPOINT`のプロセス（このリポジトリなら`java`）はその子プロセスになる。

```
無効(このリポジトリの今)        有効
PID 1  java                      PID 1  /sbin/docker-init(tini)
                                 └─ PID 7  java
```

PID 1は、Linuxでは特別扱いされるプロセスで、普通のプロセスには無い仕事が2つある。tiniは、この2つを肩代わりするためだけのプロセスである。

| PID 1の仕事 | 起きる問題 | tiniがすること |
|---|---|---|
| **シグナルを自分で処理する** | PID 1には、シグナルを受けたときの既定の動き（SIGTERMなら終了）が働かない。処理を書いていないプログラムがPID 1だと、SIGTERMを無視し、30秒後にSIGKILLで強制終了される | 受けたシグナルを子プロセスに中継する |
| **親を失ったプロセスを引き取って片付ける** | 親が先に終わったプロセスは、PID 1の子に付け替えられる。PID 1がその終了を受け取らない（`wait`しない）と、終わったプロセスの記録が**ゾンビ**として残り続ける | 引き取ったプロセスの終了を受け取り、ゾンビを片付ける |

1つ目は、このリポジトリでは問題にならない。JVMはSIGTERMの処理を自分で持っていて、受け取るとSpringの終了処理（graceful shutdown）が走る。

2つ目は、ECS Execを使うと起きうる。Execで入ったシェルや、SSMエージェントが作った子プロセスが親を失うと、PID 1の`java`の子になる。JVMはそれを片付けないので、ゾンビが溜まっていく。AWSがECS Execと一緒に`initProcessEnabled`を有効にするよう勧めているのは、このためである。

CloudFormationでは、コンテナ定義に次のように書く。このリポジトリでは、まだ設定していない。

```yaml
ContainerDefinitions:
  - Name: app
    LinuxParameters:
      InitProcessEnabled: true
```

### 技術ごとに、プロセスとスレッドの使い方が違う

「1つのプロセスで多数のスレッドを使う」のはSpring Bootの形で、すべてのサーバーがそうではない。Nginxやphp-fpmは、最初から**複数のプロセス**を起動して動く。比較は別ノートで扱う → [process-models-by-server.md](./process-models-by-server.md)

## つまずきポイント

- **「スレッドを別のプロセスに移せばよい」と考える。** スレッドは、同じプロセスのメモリを共有するために同じ場所にいる。分けるなら、役割ごとプロセスを分け、データはプロセスの外を経由して渡す（4章）
- **「サーバーは1つのプロセスしか動かせない」と考える。** OSの上では多数のプロセスが動く。1つになりがちなのはコンテナの慣習（5章）
- **「CPUは1つのプロセスしか動かせず、そのスレッドをコアの数だけ同時に動かす」と考える。** コアに載る単位はスレッドで、プロセスは問わない。4コアなら、4つの別々のプロセスのスレッドが同時に動くこともある（5章）
- **ECSで、1つのコンテナに複数の主なプロセスを入れる。** ECSはPID 1しか見ないので、子プロセスが落ちても気づかない。プロセスごとにコンテナを分け、同じタスクに並べる（5章）
- **PID 1を普通のプロセスと同じだと思う。** シグナルの既定の動きが働かず、ゾンビの片付けも任される。自分で処理しないプログラムをPID 1にするなら、`initProcessEnabled`でinitに任せる（5章）
- **コンテナの中のPIDとホストのPIDを同じものだと思う。** コンテナは別の番号体系を見せている。同じプロセスでも番号が違う（3章）
- **`main`スレッドが終わったら、アプリも終わると思う。** デーモンでないスレッドが残っている間、JVMは終わらない（3章）
- **スレッド同士で共有している値を、何も守らずに読み書きする。** 古い値を読み続けたり、書き込みがぶつかったりする。`volatile`や`synchronized`で守る（2章）
- **開発環境のプロセス構成を本番と同じだと思う。** 開発は`gradlew bootRun`なのでJavaが3つ、本番は`java -jar`なので1つ（3章）

## 用語集

- **プログラム** — ディスクに置かれた実行ファイル。動いていない状態
- **プロセス** — 実行中のプログラム1つ。OSがPIDとメモリ空間を割り当てる
- **PID（プロセスID）** — OSがプロセスに振る番号
- **PPID** — 親プロセスのPID。そのプロセスを起動したプロセス
- **スレッド** — プロセスの中で、コードを順に実行していく流れ。同じプロセスのスレッド同士はメモリを共有する
- **コア** — CPUの中で、実際に命令を実行する単位。計算する部品を1組ずつ持つ
- **論理プロセッサ（ハードウェアのスレッド）** — ソフトウェアのスレッドを載せる座席。SMTのあるCPUでは1コアに2つある
- **SMT（ハイパースレッディング）** — 1つのコアに記録（レジスタなど）を2組持たせ、2本のスレッドを同時に実行させる仕組み。計算する部品は共有するので、速さは2倍にならない
- **メモリ空間** — プロセスごとに分けられたメモリの範囲。別のプロセスからは直接読み書きできない
- **デーモンスレッド** — JVMの終了を引き止めないスレッド。デーモンでないスレッドが残っている間、JVMは終了しない
- **PID名前空間** — コンテナなどに、別のPIDの番号体系を見せるLinuxの仕組み
- **サイドカー** — 主なコンテナの補助として、同じタスク（Pod）に並べるコンテナ。ログ転送やプロキシなど
- **`Essential`** — ECSのコンテナ定義の設定。`true`のコンテナが止まると、タスクごと止まる
- **ECS Exec** — 動いているコンテナの中でコマンドを実行するECSの機能。SSMエージェントがコンテナの中で動く
- **initプロセス / tini** — PID 1として動き、シグナルの中継とゾンビの片付けだけをする小さなプログラム。ECSでは`initProcessEnabled`、Dockerでは`--init`で使う
- **ゾンビプロセス** — 終了したのに、親がその終了を受け取らないため、記録だけが残っているプロセス
- **`ps` / `top`** — プロセスの一覧を表示するコマンド。`top`は使用率の多い順に更新し続ける
- **`jcmd` / `jstack`** — JDK付属のコマンド。動いているJVMの一覧、スレッドの一覧（スレッドダンプ）を表示する
- **NLWP** — `ps`の列の1つ。そのプロセスのスレッド数（Number of Light-Weight Processes）
